# 算子性能三问：格式 / 访存 / 并行

> 面试被问「你这个 kernel 怎么优化的」时，别背结论，背**这套顺序**。
> 每一维都给出：**一个公式 → 一个数字 → 一个取舍**。
> 所有例子都来自 `aigpu-lab` 里我自己写的 kernel，数字可复现。

---

## 0. 一张速算卡（先背这个）

| 项 | 值 | 说明 |
|---|---|---|
| 卡 | RTX 4060 Laptop，24 SM | AD107，8188 MiB |
| 峰值带宽（标称） | **272 GB/s** | `specs.py`，理论值 |
| 实测带宽天花板 | **221.4 GB/s（81.4%）** | harness 平凡 kernel 测出 |
| ncu 口径峰值 | ~262 GB/s | 所以 ncu 的 92.8% 与实测 97% 不矛盾 |
| FP16 算力 | **65.2 TFLOPS** | 实测持续 SM 2655 MHz |
| Roofline 拐点 | **239.7 FLOPs/Byte** | = 65.2e12 / 272e9，AI 低于它 → memory-bound |
| 每 SM 寄存器 | 65536 个 32 位 | 256 线程 × 48 regs → 5 block/SM → 40 warp → 83% |
| fp16 上限 | 65504 | 超了变 inf，softmax 减 max 也为了这个 |
| 元素字节 | fp32 4 / fp16·bf16 2 / fp8·int8 1 / int4 0.5 | 字节账的第一项 |

## 1. 维度一：格式 —— 决定搬多少字节

### 公式

```
字节   = Σ(读的张量 + 写的张量) × 元素数 × 元素字节数
下限_t = 字节 ÷ 峰值带宽
下限_f = FLOPs ÷ 峰值算力
物理下限 = max(下限_t, 下限_f)          # Roofline
AI     = FLOPs ÷ 字节                    # < 239.7 就是 memory-bound
```

### 我的例子（融合 RMSNorm + 残差）

| 项 | 两步实现 | 融合实现 |
|---|---|---|
| 张量流 | 读 x、读 res、写 h、读 h、写 out = **5 流 = 80 MiB** | 读 x、读 res、写 out = **3 流 = 48 MiB** |
| 实测 | 390 µs | **199.9 µs** |
| 带宽 | — | 486539264 B ÷ 199.9 µs = **251.8 GB/s** |
| ncu | — | `dram__throughput **92.8%**` |

结论句：**「已经贴着带宽墙，再改 kernel 代码没有意义；能动的只有『少搬字节』。」**

### 取舍

- 换 fp8 / int8：流量再砍一半，代价是精度 + 反量化指令。
- 融合：省的是显存往返，代价是寄存器/共享内存压力上升。
- 决定权在**精度要求**，不在技术偏好。

## 2. 维度二：访存 —— 决定带宽利用率

**三个检查，必须按顺序**（前一个没修，后面白修）：

### 2.1 合并（coalescing）

一个 warp 的 32 个 lane，地址是否**连续**？

```
连续 32×4B = 128 B = 4 个 sector（32B）→ 全用上
地址间隔 = 一行的长度 → 一个 warp 碰 32 条 cache line → 扇区利用率 1/16 = 6.25%
```

**我的例子（w4 naive attention 的 QK）**：原来 `for j = tid; j < S; j += blockDim.x`，warp 内 32 个 lane 的 `j` 相邻、地址相差 `D×2 = 128 B` → 扇区利用率 **6.25%**（ncu `l1tex__t_sectors_pipe_lsu_mem_global_op_ld`）。改成 **warp-per-j + warp 内 lane 覆盖 d** 后 → **100%**，QK 从 34.31 → **14.79 ms**。

### 2.2 向量化（vectorization）

一条 load 指令搬几个字节？

| 类型 | 每指令字节 | 说明 |
|---|---|---|
| `half` | 2 | 基准 |
| `__half2` | 4 | 一个 32 位字装 2 个 half |
| `float4` / `uint4` | 16 | 128 位，最宽 |

**省的是指令条数，不是字节数**。我的 GELU 用 `__half2`（`__half22float2` + `__float22half2_rn`，全程零 `&`）从 63.1% → **81.4%**，追平 PyTorch。

> 反例：把 `float4 box` 再 `reinterpret_cast<half*>(&box)` → 取地址，变量被物化到 **local memory**，19.3%（比朴素版慢 3.3 倍）。查法：`launch__registers_per_thread` 很低 = 取地址；很高 = 寄存器溢出。

### 2.3 复用（reuse）

同一份数据被读第二次以上吗？

- block 内复用 → **共享内存**（tile）
- block 间复用 → **L2**（调 block 顺序、波次）

**我的例子（GEMM）**：naive 每线程直读全局 → 元素读次数 `2·M·N·K = 2.147e9`，**4.29 GB**；加 32×32 shared tiling 后 → **134 MB**（32 倍削减），2.42 → 1.78 ms。

### 取舍

- 向量化要求：地址 16 B 对齐 + 元素数能被 4 整除，否则退回标量。
- 共享内存不是越多越好：Ada 每 block 上限 48 KB，且会压占用率。

## 3. 维度三：并行 —— 决定能不能喂饱 SM

**三个数，从粗到细**：

### 3.1 block 数 vs SM 数

```
block 数 ÷ 24 = 每 SM 平均 block 数
每 SM warp = block 数 × (blockDim/32)   ← 上限 64
```

**我的例子（w7 PagedAttention）**：`B×H = 256` 个 warp = **32 个 block**，而卡有 24 SM → **1.33 block/SM**，每 SM 只有 10.7 warp（上限 64）。这就是它 1.51 ms 卡住的原因——**不是访存没优化，是根本没有足够的 warp 去等内存**。

解法是 split-L：把每对 (b,h) 的 2048 个 key 切成 4 段并行，grid 32 → **128**（5.33 block/SM），1.5084 → **1.2483 ms**。

### 3.2 占用率（occupancy）

每 SM 能驻几个 block，由三者最紧的那个决定：

| 限制 | 算法（256 线程/block 为例） |
|---|---|
| 寄存器 | `65536 ÷ (256 × regs)`，向下取整 |
| 共享内存 | `100 KB ÷ smem_per_block`（Ada 每 SM 100 KB） |
| 线程 | `1536 ÷ 256 = 6` |

48 regs → 5 block → 40 warp → **83%**；56 regs → 4 block → 32 warp → **67%**。

### 3.3 ILP（每线程几个独立 load）

- 1 个：全串行，靠 warp 切换藏延迟
- 2 路展开：每迭代 2 token × 2 数组 = **4 个独立 load**
- 上限：**寄存器**

**我的例子（w7）**：单遍 1.8897 → 2 路展开 **1.5084 ms**（1.25×）。注意单遍版比两遍版**慢**（1.8897 vs 1.25× 提升后仍不及）——因为它只有 1 个独立 load，延迟藏不住。

## 4. 30 秒口述模板

> 「我一般先算三个下限：**字节数**给带宽下限，**FLOPs** 给算力下限，取大的是物理天花板，再用 Roofline 的 AI 判断是 memory-bound 还是 compute-bound。然后用 ncu 看实际到没到——比如融合 RMSNorm 到 92.8%，就说明是 memory-bound 且已贴墙，代码层面没空间了。
>
> 没贴墙就按顺序查三件事：**warp 内地址连不连续**（合并）、**一条指令搬几字节**（向量化）、**数据有没有被重复读**（共享内存/L2）。这三样修完还慢，才是**并行度**问题——先看 grid 够不够喂满 SM，再看寄存器/共享内存有没有把占用率压下去，最后看每线程有几个独立 load（ILP）。」

## 5. 五个必被追问

| 追问 | 答法 |
|---|---|
| 「92.8% 怎么算的？」 | 48 MiB ÷ 199.9 µs = 251.8 GB/s；272 是标称，ncu 口径约 262，所以 92~96% |
| 「为什么不是 100%？」 | 尾部效应（最后几个 block 不满）+ 融合指令开销 + 未对齐访问 |
| 「怎么确认是 memory-bound？」 | 算 AI：融合 RMSNorm 约 8，远低于拐点 239.7 → 必然 memory-bound |
| 「共享内存有没有 bank conflict？」 | `ncu --metrics l1tex__data_bank_conflicts_pipe_lsu_mem_shared`；32 位一行时冲突最狠 |
| 「再快一倍，你动哪里？」 | **不动 kernel**，动算法：减字节（量化/融合）或换布局。这是唯一能突破带宽墙的方向 |

## 6. 反面答法（一说就露）

| 会说 | 为什么错 |
|---|---|
| 「我调了 block size 和 num_warps」 | 那是最后一维的手段，不是第一反应 |
| 「我把 kernel 写得更紧凑了」 | 没有数字，无法验证 |
| 「我的带宽到 79%，还有 21% 可以优化」 | 分母如果是 272 标称，那么 221.4 才是真天花板 → 79% 相当于**已经 97%** |
| 「所有算子都是 memory-bound」 | 反例就在我自己的表里：softmax 0.2160 ms 时 ncu 是 **SM 87.96% / DRAM 38.20%** → 它是 SM-bound（20 次 `__syncthreads` 吃掉了发射带宽），不是带宽问题 |

## 7. 一分钟自测

1. fp16 的 `matmul` 在 4060 上，AI 低于多少就一定是 memory-bound？
2. 一个算子读 2 个 fp16 张量、写 1 个，每个 1024×1024，带宽 221.4 GB/s，理论下限多少毫秒？
3. warp 里 32 个 lane 地址间隔 128 B，扇区利用率是多少？代价是多少倍？
4. `__launch_bounds__(256, 4)` 是让编译器干什么？代价是什么？
5. 你的 kernel 带宽到了 79%（对标称），下一步该做什么？

<details>
<summary>答案</summary>

1. **239.7 FLOPs/Byte**（65.2 TFLOPS ÷ 272 GB/s）。
2. 3 × 1024² × 2 B = 6.29 MB；6.29e6 ÷ 221.4e9 = **28.4 µs**。
3. 每个 lane 落一个独立 sector（32 B），只用 2 B → **1/16 = 6.25%**；代价是**读 32 倍的数据**。
4. 强制每 SM 至少驻 4 个 block → 把寄存器压到 ≤64；**代价是可能溢出到 local memory**（反而变慢）。
5. 先确认分母：79% × 272 = 215 GB/s，而真天花板 221.4 → 实际已 **97%**。**该停手换项目，或改算法减字节**。

</details>
