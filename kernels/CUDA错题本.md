#### ❌ E-01　全局索引算错（off-by-one）

**我问**：`blockIdx.x = 2`、`blockDim.x = 256`、"这是块内第 99 个线程"，全局索引是多少？

**你答**（m01900 原话）：「全局索引是 `2*256+99-1`」→ 610

**错因**：以为"第 99 个"要先减 1 换成 0-based 再代入。

**正解**：
```
i = blockIdx.x * blockDim.x + threadIdx.x = 2 * 256 + 99 = 611
```

**要害**：`threadIdx.x` **本身就是 0-based 的索引**。"第 n 个线程"的 `threadIdx.x` 就是 `n`，不是 `n-1`。

```
threadIdx.x:   0     1     2     3   ...   99
             第1个  第2个  第3个  第4个     第100个
```

**为什么危险**：这类 `-1` 不会让结果整体错，而是**"大部分对、边界错"**——某个线程漏算或重算一个元素。这是最难查的一类 bug，因为它不崩、不报错，只是数值轻微不对。

**状态**：🟡 已自我纠正（m01903 改成 `2*256+99`，正确）

#### ❌ E-02　把「线程束分化」当成「一部分线程等另一部分」

**你答**（m01903 原话）：「tid<stride 导致线程束分化，加入这个命令后，会同步吗？**分化本来就是一部分等另一部分吧，没效果吧？**」

**错了两层**：

**第 1 层——分化不是"等"**：
分化（divergence）= 同一个 warp 里线程走了不同分支，硬件**把两条路径串行执行两遍再汇合**（reconverge）。
是「**同一批线程分两次干活**」，不是「一批等另一批」。而且范围是**一个 warp（32 线程）内部**。

第 2 层——屏障是"块"级，跨 warp：
`__syncthreads()` 要求 **block 内全部线程**到达，不是 warp 内。

**由此推出的致命后果**（这才是这题的重点）：

```cpp
// ❌ 会挂死的写法
if (tid < stride) {          // tid >= stride 的线程 —— 整个 if 都进不去
    s[tid] += s[tid + stride];
    __syncthreads();         // ← 这些线程永远执行不到这一行
}
```

`tid >= stride` 的线程永远到不了屏障，而已到达的线程一直等 → **挂死（hang）/ 未定义行为**。

```cpp
// ✅ 正确
if (tid < stride) {
    s[tid] += s[tid + stride];
}
__syncthreads();             // ← 必须在 if 外面
```

**口诀**：**屏障是"全员集合点"，不能让任何人缺席。**

**官方规定**：`__syncthreads()` 只有在**条件对整个 block 都相同**时，才允许放在条件语句里；否则未定义行为。

**状态**：🔴 待验证

#### ❌ E-03　把 `__syncthreads()` 说成「线程束同步」

**你答**（m01903）：「这是线程束同步」

**正解**：`__syncthreads()` 是**块级（block-level）**屏障，最多覆盖 1024 个线程 = 32 个 warp。

**三层同步对照表**：

| 机制 | 作用范围 | 显式还是隐式 |
|---|---|---|
| warp 内同步 | 32 线程 | **隐式**（同 warp 线程一起发射） |
| `__syncwarp()` | 32 线程 | 显式（Volta 后线程可独立调度才需要） |
| **`__syncthreads()`** | **整个 block（≤1024 线程）** | **显式，块级屏障** |

**为什么必须是块级**：共享内存是**块内共享**，所以同步也必须是块级。若只有束级同步，block 内 8 个 warp 之间交换数据就是未受保护的竞态。

**顺带记住这个骨架（LayerNorm / RMSNorm / Softmax 通用）**：

```cpp
if (tid == 0) {
    s[0] = rms;              // ① 归约结果写回共享内存
}
__syncthreads();             // ② 块级屏障（不是束级！）
float my_rms = s[0];         // ③ 所有线程都读到同一个值
```

**状态**：🔴 待验证

#### ❌ E-04　树形归约骨架答不出

**你答**（m01903）：「不知道，骨架是什么？归约忘记了」

**正解（默写级）**：

```cpp
s[tid] = 局部部分和;                          // ① 每个线程写自己那一格
__syncthreads();                              // ② 等大家都写完

for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (tid < stride) {
        s[tid] += s[tid + stride];            // ③ 前一半线程把后半部分加过来
    }
    __syncthreads();                          // ④ 在 if 外面！每轮都要
}
// 循环结束时 s[0] = 总和
```

**`stride` 是什么**：这一步里**两个要相加的元素之间隔多远**。从 `blockDim.x / 2` 开始，每轮**减半**（256→128→64→…→1，共 8 轮）。

**8 个元素的完整走法**（3+1+4+1+5+9+2+6 = 31）：

```
初始:      s = [3,  1,  4,  1,  5,  9,  2,  6]

stride=4:  tid0: s[0] += s[4] →  3+5  = 8
           tid1: s[1] += s[5] →  1+9  = 10
           tid2: s[2] += s[6] →  4+2  = 6
           tid3: s[3] += s[7] →  1+6  = 7
           (tid4~7 不动)
           → s = [8, 10, 6, 7, ...]
           __syncthreads();

stride=2:  tid0: s[0] += s[2] →  8+6  = 14
           tid1: s[1] += s[3] → 10+7  = 17
           → s = [14, 17, ...]
           __syncthreads();

stride=1:  tid0: s[0] += s[1] → 14+17 = 31
           → s = [31, ...]   ✅
```

**"归约"是什么**：N 个输入 → 1 个输出。求和、求最大值、求平均，都是归约。

**为什么分两步**：一行 4096 个数，若让线程 0 一个人从头加到尾 = 4096 次串行。256 个线程各加 16 个再合并 → 快 256 倍。

**状态**：🔴 待验证

#### ⚠️ E-05　bank conflict 没答出来（未答）

**我问**：`__shared__ float s[256];` 线程 `tid` 读 `s[tid]` 有没有 bank conflict？读 `s[tid * 2]` 呢？

**你答**：说的是动态共享内存的知识（本身对，但不是我问的）

**正解**：
- 共享内存有 **32 个 bank**，每个 **4 字节**宽；地址按 `(地址 / 4) % 32` 分到 bank
- **`s[tid]`：无冲突** —— 线程 0 读 bank 0、线程 1 读 bank 1……线程 31 读 bank 31；线程 32 又回到 bank 0，但那是**另一个 warp**，不冲突
- **`s[tid * 2]`：2-way conflict** —— 32 个线程只用到了 16 个 bank（bank 0,2,4,…,30），每个 bank 要服务 2 个线程 → **访问被串行化，慢一倍**

**状态**：🔴 待验证

### 2026-10-13 · 第 1 次实操（写 RMSNorm kernel，第一次提交）

**你提交的代码（原样，m01943）**：

```cpp
__global__ void rmsnorm_kernel(const half* __restrict__ x,
                               const half* __restrict__ w,
                               half* __restrict__ out,
                               const int rows,
                               const int cols,
                               const float eps) {
    const long long i = (long long)blockIdx.x * blockDim.x + threadIdx.x;
    const long long n = (long long)rows * cols;
    if (i < n) {
        out[i] = x[i] * x[i];          // ← 占位。你要把这行换成真正的 RMSNorm
    }
    __syncthreads();
    float sum += out[i]
    float mean = sum / n + eps
    float rms = sqrt(mean)
}
```

**先说做对的**（错题本也要留对的部分）：
- ✅ **主干三步抓对了**：先算平方和 → 除以元素个数得 mean → 开方得 rms。顺序是对的。
- ✅ **记得要用 `__syncthreads()`**（虽然位置和范围都用错了）。
- ✅ 保留了 `if (i < n)` 的边界防护意识。

#### ❌ E-06　并行映射结构性错误：一行被拆到 16 个 block 里（**本次最严重**）

- **现象**：用 `i = blockIdx.x * blockDim.x + threadIdx.x` 一维铺开
- **算一下**：`n = rows × cols = 2048 × 4096 = 8,388,608`，`threads = 256` → `blocks = 32768`
  一行 4096 个元素 → **一行被拆到 4096 / 256 = 16 个不同的 block 里**
- **为什么致命**：`__syncthreads()` **只在 block 内生效，跨 block 无法同步**。
  所以 block 0 只能知道它那 256 个元素的平方和，**永远算不出整行的 rms**。
  **这个写法不是"细节写错"，是结构上就不可能对。**
- **正解**：换成「**一个 block 管一整行**」——`row = blockIdx.x`、`blocks = rows`，块内 256 个线程分摊这一行的 4096 个元素
- **状态**：🔴 待验证

#### ❌ E-07　`float sum += out[i]` 语法错误（且三行全缺分号）

- **错**：`+=` 是复合赋值，必须先声明再赋值。`float sum += x;` 不是合法的变量声明。
- **正解**：`float sum = 0.f;` 然后再 `sum += ...;`
- **顺带**：`float sum += out[i]` / `float mean = ...` / `float rms = ...` **三行都缺行尾分号** → 编译直接失败
- **要害**：说明**没编译就提交了**。写 kernel 的习惯应该是"写完就编译"——编译器是最便宜的评审
- **状态**：🟡 低风险（编译器会拦），但习惯要改

#### ❌ E-08　归一化分母用错：应该是 `cols`，不是 `rows * cols`

- **你写**：`mean = sum / n`，其中 `n = rows * cols = 8,388,608`
- **错因**：RMSNorm 是**逐行**归一化——每一行用自己的 rms，分母是**这一行的元素个数 = `cols` = 4096**
- **要害**：`rows * cols` 是**整个张量**的元素数。RMSNorm **不跨行**，这是它必须"按行"处理的根本原因
- **状态**：🔴 待验证

#### ❌ E-09　拿 `out` 当草稿纸

- **你写**：`out[i] = x[i] * x[i];` 然后再 `sum += out[i]`
- **错因**：`out` 是**最终输出**张量。把它当中间结果的暂存区，就再也放不下真正的结果了
- **正解**：平方和算在**局部变量 + 共享内存**里，`out` 只在最后写一次
- **状态**：🔴 待验证

#### ❌ E-10　忘了归约：256 个线程各有一个 `sum`

- **现象**：每个线程的 `sum` 只包含**它自己那一个元素**，却被直接当成"整行的和"
- **正解**：256 个部分和必须**合并成 1 个**——这正是树形归约（E-04）要干的事
- **状态**：🔴 待验证

#### ❌ E-11　缺最后一步：算出 rms 之后没有做归一化

- **你写**：算完 `rms` 函数就结束了，没有写回 `out`
- **正解**：还要 `out[row * cols + col] = (float)x[...] / rms * (float)w[col];`
- **顺带**：参数 `w` **从头到尾没被用到**——权重没乘，RMSNorm 就没做完
- **状态**：🔴 待验证

#### ⚠️ E-12　fp16 精度：`x[i] * x[i]` 在 half 下计算

- **问题**：`half * half` 在 CUDA 里按 **fp16** 运算，平方会掉精度、甚至溢出（fp16 最大约 65504）
- **正解**：**平方和必须用 `float` 累加**：`float v = (float)x[idx]; sum += v * v;`
- **状态**：🔴 待验证

#### ⚠️ E-13　`sqrt` vs `sqrtf`

- device 代码里处理 float 应该用 `sqrtf`；写 `sqrt` 会走 double 路径，慢且不必要
- **状态**：🟡

#### ❌ E-14　每线程元素数算错（差了 128 倍）

**算一下**：

```
总线程数   = grid × block = 128 × 128 = 16,384
N          = 4,194,304
每线程元素 = 4,194,304 ÷ 16,384 = 256        ← 不是 2
```

| 你的答案 | 实际 |
|---|---|
| grid = 128 | 128（数字本身没错，错在没说清依据） |
| block = 128 | 128 |
| **每线程 2 个元素** | **每线程 256 个元素（差 128 倍）** |

**错因**：`grid` 和 `block` 是先拍的，元素数**没有回头验算**。1.6 万个线程去搬 419 万个元素，每个线程自然要搬 256 个。

**如果你想真做到"每线程 2 个元素"**：

```
需要线程数 = 4,194,304 ÷ 2 = 2,097,152
block = 128 时 → grid 必须是 16,384，不是 128
```

**顺带一个设计问题（这才是深层毛病）**：`grid=128` 在你这张卡上**占用率严重不足**。

```
你的卡：24 个 SM，每个 SM 最多 1536 个线程 → 在飞线程上限 = 24 × 1536 = 36,864
你开的：128 block × 128 线程 = 16,384 线程
占用率 ≈ 16,384 / 36,864 = 44%
```

而 `grid=128` 摊到 24 个 SM 上只有 **5.3 个 block/SM**——有些 SM 只分到 5 个 block，**剩下的线程槽位全空着**。纯访存 kernel 靠的就是"足够多的线程在飞来掩盖显存延迟"，44% 占用率会直接压住带宽。

**根治方法（记住这个顺序，绝对不要倒过来）**：

```
① N 是多少？              → 2^22 = 4,194,304
② 硬件同时能跑多少线程？   → 24 SM × 1536 = 36,864
③ 每线程几个元素？        → 4,194,304 ÷ 36,864 ≈ 114
                            （或主动取整成 8 / 16 / 32 这种好数）
④ 反推 grid × block       → 先定 block=256，再算 grid
```

**先 ① 再 ④。先拍 grid/block 再回头算元素数，就会得到刚才那个 128 倍的误差。**

**状态**：🔴 待验证

#### ❌ E-16　把「每 SM 线程上限」当成了「每 block 线程上限」

**两个上限完全不是一回事：**

| 限制 | 值 | 含义 | 怎么查 |
|---|---|---|---|
| `maxThreadsPerBlock` | **1024** | **一个 block** 最多 1024 个线程 | 硬性规定，所有架构相同 |
| `maxThreadsPerMultiProcessor` | **1536** | **一个 SM** 最多同时驻留 1536 个线程 | 逐代变化（Ada = 1536） |

**`block = 1536` 是非法 launch** → 直接报 `invalid configuration argument`（`cudaErrorInvalidConfiguration`），kernel 根本起不来。

**为什么 block 卡在 1024**：block 是**调度与同步的基本单位**。一个 block 的线程必须能**同时驻留在同一个 SM 上**，还要共享同一块共享内存、共享同一个 `__syncthreads()` 屏障。1024 = 32 个 warp，是硬件在「同步开销」和「并行度」之间划的那条线。

**把这两个数摆到一起看，区别就出来了**：

```
block = 256   →  一个 SM 里同时装 6 个这样的 block，合计 1536 线程   ← ✅ 合法，满 occupancy
block = 1536  →  一个 block 就想要 1536 线程                        ← ❌ 非法，1024 就封顶
```

**要害一句话**：**想占满 1536，靠的是「多个 block 并存」，不是「一个大 block」。**

这正是为什么 `block=512` 能行（`1536 ÷ 512 = 3` 个并存，正好满），而 `block=1536` 不行。

**状态**：🔴 待验证

#### ❌ E-17　树形归约要求 `blockDim` 必须是 2 的幂

**你问**：「归约是 log2(1536)?」

**先算这个数**：

```
log₂(1536) = log₂(3 × 512) = log₂3 + 9 ≈ 1.585 + 9 = 10.585
```

**不是整数——这就是雷。**

树形归约骨架（E-04）是：

```cpp
for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (tid < stride) s[tid] += s[tid + stride];
    __syncthreads();
}
```

`stride >>= 1` 是**整数移位**。当 `blockDim.x = 1536`：

```
768 → 384 → 192 → 96 → 48 → 24 → 12 → 6 → 3 → 1 → 0      （10 轮）
```

**看 6 后面是 3，不是 1.5——整除开始"漏拍"了。** 追最后三轮：

```
stride = 6 :  s[0..5] += s[6..11]   →  s[0]~s[5] 各是一个部分和
stride = 3 :  s[0..2] += s[3..5]    →  s[0]~s[2] 各是一个部分和
stride = 1 :  s[0]    += s[1]       →  只有 s[0]+s[1]
              ★ s[2] 永远没被加进 s[0] ★
```

**结果错了——`s[2]` 那一份贡献被永久丢掉。不崩、不报错、就是数值不对。**

**正确做法**：`blockDim.x` 取 **2 的幂**，`stride >>= 1` 才能精确对半砍到 1：

```
512 → 256 → 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1        （9 轮，log₂512 = 9 ✅）
```

**通用公式（把「必须」两个字刻进去）**：

```
树形归约层数   = log₂(blockDim.x)         ← 仅当 blockDim.x 是 2 的幂才有意义
stride 起始值 = blockDim.x / 2
blockDim.x ∈ {128, 256, 512, 1024}       ← 合法且安全的选择
```

**能不能用非 2 的幂再补边界？** 技术上可以（加 `tid + stride < blockDim.x` 之类的保护），但代码变丑、变慢，而且**一点好处都没有**——block 大小为什么非得取怪值？

**顺带**：这一条和 E-15 是连着的。E-15 的病是「参数换了数字不换」，E-17 的病是「参数本身就选了个用不了的值」。**两条都指向同一件事：block 的大小不是随便拍的数，它被三条约束夹着——≤1024、要是 2 的幂、还要能整除 1536 才有满 occupancy。**

#### ❌ E-18　并行映射：`blockIdx.x` 乘的不是 `blockDim.x`，是「一个 block 覆盖多少个元素」（**本次最严重，连错 4 轮**）

**CUDA 黄金公式本身没错，但它有前提**：

```cpp
blockIdx.x * blockDim.x + threadIdx.x
```

**前提是：每个线程正好处理 1 个元素。**

```
每线程 1 个  →  一个 block 覆盖 blockDim.x      = 512 个元素  →  blockIdx.x 乘 512    ✔
每线程 8 个  →  一个 block 覆盖 blockDim.x × 8  = 4096 个元素 →  blockIdx.x 乘 4096
```

**`blockIdx.x` 乘的是「一个 block 覆盖多少个元素」，不是「一个 block 有多少个线程」。**
每线程 1 个时这两个数恰好相等，公式才长成那样；**一旦每线程 k 个，它们就分家** —— 这就是连错 4 轮的根。

**你 4 轮里的三种错法**：

| 轮次 | 你写的 | 后果 |
|---|---|---|
| 1 | 压根没有 `blockIdx.x` | 1024 个 block 全读 `x[0..511]`，**99.99% 的数据没人读** |
| 3 | `blockIdx.x * blockDim.x` | 每 block 只覆盖 512 个 → 相邻 block 大面积重叠，且 **87% 漏读** |
| 4 | 同上，且上界写成 `n/(blockDim.x*8)` | 算出来的 `1024` 是 **block 的个数**，不是每 block 的元素数 → 每线程只跑 2 轮 |

**正确的三段式**（以每线程 `K = 8` 为例）：

```
每线程元素数   K    = 8
block 的跨度   SPAN = blockDim.x * K        = 4096
本 block 起点  base = blockIdx.x * SPAN     = blockIdx.x * 4096
循环：i 从 tid 起、步长 blockDim.x、上界 SPAN
      全局地址 = base + i
```

**★ 自检法（写完映射必须心算一遍，比编译还快）**：

> **把所有 block 读到的地址并起来，必须恰好等于 `0 .. n-1`，每个元素不多不少正好一次。**

不重、不漏。第 3 轮那版：**既重**（block 0 和 block 1 共享 512 个地址）**又漏**（87% 没读）——一算就现形。拿 `blockIdx.x = 0` 和 `blockIdx.x = 1` 纸笔展开一遍最直观。

#### 📘 E-35　把「声明」当成「实参」贴进 `<<<>>>` 后面的括号

```cpp
gelu_kernel<<<blocks, threads>>>(const half* __restrict__ x, half* __restrict__ out, const int n4);
                                 ↑↑↑ 这是声明，不是值
```

`<<<>>>` 后面的括号里要的是**变量名**（`x_ptr`、`out_ptr`、`n4`），
不是 kernel 的**形参列表原文**。

**这暴露出一个更根本的混淆** —— `<<<>>>` 和 `()` 是**两个不同的位置**：

```cpp
gelu_kernel <<< blocks, threads >>> ( x_ptr, out_ptr, n4 );
              └──── 启动配置 ────┘   └─── 实参表 ───┘
              怎么启动                传什么进去
```

- `<<<blocks, threads, smem_bytes>>>`：**怎么启动**（多少 block、每 block 多少线程、可选共享内存字节）
- `(...)`：**传什么进去**（按 kernel 形参表的**顺序、个数、类型**一个一个对上）

**问「括号里填什么」之前，先回答：这是哪个括号？**

#### `blocks = rows` 碰巧对，但道理是错的

`:56` 写 `const int blocks = rows;` —— 对当前 shape 结果正确
（`rows` = 2048，而正确的 grid 也是 `n4 / threads` = 2048），**但纯属巧合**：

- `rows` 是**行数**，是 rmsnorm / softmax 才有的概念
- gelu 是纯逐元素算子，**没有「行」**，只有「一共几个元素」
- 正确写法：`const int blocks = (n4 + threads - 1) / threads;`

**这是「参数换了，公式里的数字没跟着换」的第 6 次**（E-01 / E-14 / E-15 / E-17 / E-34）。

#### 📘 E-36　★ 取局部变量的地址 → 变量被赶进 **local memory**

19.3% 那个数字的根因**不在向量化**，在这两行：

```cpp
:28   half* h    = reinterpret_cast<half*>(&box);     // ← 取 box 的地址
:32   half* outh = reinterpret_cast<half*>(&obox);    // ← 取 obox 的地址
```

**局部变量默认住在寄存器里 —— 而寄存器没有内存地址。**

所以只要你写一次 `&变量`，编译器就**必须**给这个变量分配一块**内存**（local memory）。
local memory 物理上在 **DRAM** 里（走 L1/L2 缓存）：

| | 朴素版 | float4 版（坏） |
|---|---|---|
| 全局读 | 1 次 × 16 字节 | 1 次 × 16 字节 |
| **local 访存** | **0** | **18 次**（8 个 half 的拆/装，每次 2 字节） |
| 全局写 | 1 次 × 16 字节 | 1 次 × 16 字节 |
| 实测 | 0.1956 ms | **0.6390 ms（慢 3.3 倍）** |

**关键：`box` 才 16 字节 = 4 个寄存器，一点都不「放不下」。**
这不是**寄存器溢出**（变量太多塞不下，编译器被逼的），是**你主动要了一个地址**：

| | 寄存器溢出 | **取局部变量地址** |
|---|---|---|
| 谁导致的 | 编译器被逼 | **你要求的** |
| 症状 | `launch__registers_per_thread` **很高**，occupancy 被寄存器卡住 | `launch__registers_per_thread` **很低**（变量都搬走了） |
| 变量大小 | 太大 | **多小都中招** |

**⇒ 规矩：CUDA kernel 里不要对局部变量取地址（`&var`），除非你真的需要指针。**

#### 📘 E-37　`__half2` 为什么能绕开这个问题

`float4` 的问题：**它里面装的是 `float`，而你要的是 `half`** —— 换类型就得换指针，换指针就得取地址。

`__half2` 不一样：**它本身就是「打包好的 2 个 half」**，库函数直接给你 `float2`：

```cpp
float2 f = __half22float2(x2[k]);      // 4 字节读 → 寄存器里的两个 float
...
o2[k] = __float22half2_rn(g);          // 寄存器里的两个 float → 4 字节写
```

**全程没有 `&`，因为不需要换类型。**
`float4` 是「一次搬 16 字节的**箱子**」，`__half2` 是「**已经是你想要的那种东西**」。

### E-58 `partial[]` 的大小 = 线程数，不是每段 j 数

- **错**：`blockDim=128` 时答「partial[] 要取 512」；`blockDim=512` 时答「取 128」。把**段长 `seg`** 和**数组长度**搞混了。
- **正解**：每个线程写 1 个 float 到 `partial[threadIdx.x]` ⇒ 数组长度 = `blockDim.x`。
  - `blockDim=128` → `partial[128]`
  - `blockDim=256` → `partial[256]`
  - `blockDim=512` → `partial[512]`
- **连带越界**：代码里声明 `__shared__ float partial[SM_THREADS]`（=256），若 launch 成 512 线程 → 下标 256..511 越界写共享内存（静默错，可能改掉别的变量）。**声明必须用运行时 `blockDim.x`，或者用 `extern __shared__` + launch 时传大小。**
- 口诀：**「每个线程一个槽，槽数就是线程数」**

### E-59 MB 是 1024 还是 1000（E-49 的兄弟，第 2 次）

- **错**：L2 = 24 MB，`24*1000/128 = 187.5` → 答 187。
- **正解**：显存/缓存的 MB 按 **MiB（1024×1024）** 算：`24×1024 ÷ 128 = 192` 个。
- 口诀：**「字节换算一律 1024，带宽（GB/s）才用 10⁹」**——和 E-49 是同一条纪律的两面。

### E-60 降寄存器 ≠ 调 block 数

- **错**：答「调整线程数量以及 block 数量，使寄存器使用少一点」。
- **正解**：寄存器是 **per-thread** 的，由编译器按代码分配，**和 block 数、grid 数无关**。降寄存器的手段：
  1. 减少同时 live 的变量
  2. 减小 `#pragma unroll` 展开倍数
  3. 拆 kernel（一个 kernel 别干三件事）
  4. `__launch_bounds__(threads, minBlocksPerSM)` 让编译器自己压
- 参考数：Ada 每 SM 65536 个寄存器 / 最多 1536 线程 ⇒ **每线程 ≤42 才可能 100% occupancy**；72 个寄存器 + 256 线程 → 只能 3 个 block → 50%。

  理论最短时间 = warp 指令总数 ÷ (SM 数 × 每 SM 调度器数 × 主频)

## 2026-10-21 知识点补记（ILP-4 与寄存器预算）

### K-01 为什么 ILP 取 4 份（2 / 4 / 8 的账）

**结论：4 是「寄存器预算」和「延迟覆盖」两条线的交点，不是定律。**

延迟覆盖这一侧：shuffle 一轮延迟约 25 周期，一个调度器每周期能发 1 条指令 →
要填满得同时有 ~25 条独立指令可发。4 条链在 shuffle 阶段每轮 = 4 shfl + 4 add = 8 条独立指令，
配合 occupancy 100% 时其他 warp 一起填，够用；2 条链只有 4 条，填不满。

寄存器预算这一侧（Ada：每 SM 65536 个寄存器，每线程上限 255）：

| 每线程寄存器 | 256 线程/block 能装 | occupancy |
|---|---|---|
| 40 | 6 个（61440） | **100%**（1536 线程） |
| 48 | 5 个（61440） | 83%（1280） |
| 56 | 4 个（57344） | 67%（1024） |

- 加 4 条链 ≈ **+6~8 个寄存器**（4 个 `a` + 2~4 个 K 的临时值）→ 40 → 46~48 → occupancy 掉到 83%。
- 加 8 条链 ≈ **+14~16 个** → 55~56 → 掉到 67%，而 8 条链早就把延迟洞填满了，纯亏。
- **掉 17% occupancy 换 4 倍 ILP 是划算的；掉 33% 换 8 倍是亏的。**

### K-02 怎么确认「没超寄存器预算」（Q5）

三种方法，按方便程度排：

1. **看编译日志**（最快）：编译时加 `-Xptxas -v`，nvcc 会打印
   ```
   ptxas info: Used 46 registers, 4 bytes smem, ...
   ```
   用 `load_inline` 时：`extra_cuda_cflags=["-O3","--use_fast_math","-lineinfo","-Xptxas","-v"]`，
   再把 build 的 verbose 打开（`--verbose-build`）。
2. **ncu**：
   ```bash
   ncu --metrics launch__registers_per_thread,launch__occupancy_limit_registers,sm__warps_active.avg.pct_of_peak_sustained_active python ...
   ```
   `launch__registers_per_thread = 46` 就是答案；`launch__occupancy_limit_registers` 告诉你
   「寄存器这一项把 occupancy 卡在多少」。
3. **手算**：`每线程 regs × 每 block 线程数 × 能装的 block 数 ≤ 65536`，反解 block 数。

**判据：≤42 才能 100%；>48 说明 4 条链太贵，降到 2 条。**

### K-03 「寄存器数 = 变量数」这个模型哪里对、哪里错

**对的部分**：一个 `float` 占 1 个寄存器（32 位 = 4 字节），`half` 单独存也要占一整个寄存器
（硬件最小 32 位）。所以「通篇 float、只有输入输出是 half」时，寄存器压力确实按 float 算。

**错的部分（三条）**：

1. **编译器会复用寄存器**：两个生命周期不重叠的变量共用一格。所以寄存器数 ≈ **「同时活着的变量数」+ 临时值**，不是「代码里变量总数」。
2. **不是所有变量都进寄存器**：
   - 数组（除非编译器完全展开且下标是常量）→ local memory
   - 取了地址的变量（`&x`）→ local memory（E-38）
   - 超出预算的部分 → 溢出到 local memory（spill）
3. **还有非变量的开销**：地址计算、循环下标、类型转换的中间值，都要寄存器。

一句话：**「同时活着的 float 个数」是下界，「变量总数」是上界，真实值由编译器决定，只能用 `-Xptxas -v` 或 ncu 量。**

#### ❌ E-55　`pv_kernel` 把「求和维 j」和「输出维 d」搞混了
- **你写**：
  ```cuda
  for(int d = 0; d < D; d++) {                       // ← 没用 tid，256 个线程算同一个 d
      float acc = 0.f;
      for(int i = tid; i < S; i += blockDim.x)
          acc += P[p_base + i * S + i] * V[v_base + d];   // ← 两处索引都错
      O[o_base + i] = __float2haf(acc);                    // ← i 已出作用域 + 拼写错
  }
  ```
- **四个错**：
  1. 外层 `for(d)` **没有映射到线程**：256 个线程算的是同一个 `d`，结果互相覆盖。
  2. `P[p_base + i*S + i]`：P 的一行是 `p_base + j`。乘 `S` 是**跨行**的步长，会指到别的行去。
  3. `V[v_base + d]`：缺 `j*D`，永远只读第 0 个 token 的第 d 维。
  4. `O[o_base + i]`：`i` 是内层 `for` 里声明的，**出了作用域就不存在**（编译错）；且索引本该是 `d`。
- **正解（A 方案，6 行）**：
  ```cuda
  for (int d = threadIdx.x; d < D; d += blockDim.x) {
      float acc = 0.f;
      for (int j = 0; j < S; ++j)
          acc += __half2float(P[p_base + j]) * __half2float(V[v_base + (size_t)j * D + d]);
      O[o_base + d] = __float2half(acc);
  }
  ```
- **记忆点**：`O[i,d] = Σ_j P[i,j]·V[j,d]` —— **乘的是 j，输出的是 d**。`j` 在 P 里是行内的连续下标（`p_base+j`），在 V 里是**行号**（`j*D`）。

#### ❌ E-56　`__shared__ float x_exp[1024]` 把 S 写死（E-39 同类，第 3 次）
- kernel 形参有 `int S`，数组却固定 1024。S=512 时浪费，S=2048 时**越界写共享内存**。
- 而且这 4 KB 根本不必存：第三趟重算 `expf(v-max)` 即可（多一次 exp，省 4 KB 共享内存）。
- **通用写法**：`extern __shared__ float smem[];` + host 传字节数，或按 `S` 动态算。

#### ❌ E-57　`__float2haf`（拼写）

#### ❌ E-64　不会算「相邻 lane 的地址差」，且 sector 概念是错的
- **你答**：地址差"4 个字节吧？"；"一个 sector 就是 128 元素"；"一次 warp load 请求 4 个 sector"；`32*32*4 = 4096 B`；利用率 12.5%
- **正解**（D=128、half、相邻 lane 处理相邻 j）：
  - 地址差 = `D × 2 = 256 B`（**不是 4**）
  - 32 个 lane 落在 **32 个不同的 32 B sector** 上，一次 warp load 搬 `32 × 32 = 1024 B`
  - 有用字节 = `32 × 2 = 64 B` → 利用率 **64/1024 = 6.25%**
  - **这个比例与 D 无关**（D=64 时也是 6.25%），因为每个 lane 都独占一个 sector
- **两条必须背死的数**：**sector = 32 B；cache line = 128 B = 4 个 sector**。没有"sector 等于多少元素"这种说法。
- **口诀**：**地址 = 基址 + 下标 × 元素字节数**；相邻 lane 处理相邻 j → 差 `D×2`；想让它变成 4 B 就得让 lane 去分 d（warp-per-j 的原理）。

#### ❌ E-65　online softmax 的 `acc` 写成除法（把"最后一步"当成"循环内更新"）
- **你答**：`acc = l_new / l`（把输出归一化那一步写进了循环）
- **正解四行**：
  ```
  m_new = max(m_old, rowmax(s))
  alpha = exp2((m_old - m_new) * 1.44269504)      // = e^(m_old-m_new)
  acc   = acc * alpha + dot(p, v)                 // 旧输出缩放后 + 新块贡献
  l     = l   * alpha + rowsum(p)                 // 旧归一化因子同样缩放
  ```
  循环结束后：`o = acc / l`（**这一步在循环外**）。
- **记住分工**：`acc`/`l` 每轮都要"**乘 alpha 再累加**"；`/ l` 只做一次，在最后。

#### 🔴 E-49　第 3 次：`48 MiB → 165.87 GB/s`
- **你答**：`48/1024/0.0002826 = 165.87`，60.98%
- **正解**：`48 MiB × 1024 × 1024 = 50,331,648 B` → `÷ 0.0002826 s = 178.1e9 B/s` → **178.1 GB/s**，`178.1/272 = 65.5%`
- **MiB / GB 的区别（你问的那句）**：
  - **MiB 是数据量**，二进制：1 MiB = 1024² B（内存/张量大小按这个）
  - **GB/s 是速率**，厂商规范用十进制：272 GB/s = 272 × 10⁹ B/s
  - 所以：**MiB → 字节乘 1024²；字节 → GB/s 除 1e9**。只有想要 **GiB/s** 时才除 1024³。
  - 你做的 `48/1024` 是"乘反而除"，只错了一半；少了第二个 1024，又错一半。

#### 🟡 E-52　第 3 次（Q5(c)）：DRAM 已 92.8% 时，方向答成"提高寄存器数量"
- **错在**：寄存器数量不减少显存字节，只会掉 occupancy。DRAM-bound 的前提不变，加寄存器 = 纯亏。
- **正解**：DRAM 到墙后，能动的**只有"总字节数"**这一件事：融合（3N 已最少）、量化（fp16→fp8/int8）、少读一遍。都做不了 → **收工**。
- **口诀**：**带宽到墙，唯一变量是字节数；调参永远不改变字节数。**
