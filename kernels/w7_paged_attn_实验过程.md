# w7 PagedAttention decode —— 实验过程与结论

> 手写 CUDA，从零实现 PagedAttention 的 decode kernel，在 RTX 4060 Laptop 上从 2.36 ms 优化到 1.04 ms（其中量化那一步是唯一的赢，另三条量化分支都是反例）。
> 本文记录每一步改了什么、为什么快、以及为什么停在这里。
> 数据来源：`results/kernels.md`（每次覆盖）+ 本文表格（手动维护，留历史）。

---

## 1. 问题

decode 阶段每个请求只有 **1 个 query token**，但要和 **2048 个历史 token** 的 KV cache 做 attention。
KV cache 存在固定大小的物理块里，不连续；靠一张 `block_table` 做逻辑块 → 物理块的映射。这就是 vLLM 的 PagedAttention。

| 项 | 值 |
|---|---|
| case | `B=8, H=32, L=2048, D=128, BS=16, MAXB=128, NB=1024` |
| dtype | fp16 |
| q | `[B, H, D]` = 64 KiB |
| k_cache / v_cache | `[NB, BS, H, D]` = 各 128 MiB |
| block_table | `[B, MAXB]` int32 |
| out | `[B, H, D]` = 64 KiB |

## 2. 字节账：这是一个纯带宽问题

真正必须从显存读的是 **KV cache 256 MiB**（q、out、block_table 都是 KB 级）：

```
流量 = 256 MiB = 268,566,528 B
算力 = 4·B·H·L·D = 8.59 GFLOP
AI   = 8.59e9 / 268.6e6 = 32 FLOPs/Byte
```

Roofline 拐点是 **239.7 FLOPs/Byte**，32 远小于它 ⇒ **memory-bound**，算力完全不是瓶颈。

| 参照 | 带宽 | 理论下限 |
|---|---|---|
| 标称峰值 | 272.0 GB/s | 0.99 ms |
| **实测天花板**（`scale` kernel 打出来的） | **221.4 GB/s** | **1.21 ms** |
| fp16 最优（④ split-L） | 215.1 GB/s | 1.2483 ms |
| **全表最优（⑤ K 量化）** | **194.4 GB/s** | **1.0419 ms** |

> 本文所有“占峰值”都按 272 标称算，“占实用”按 221.4 算。**只有后者有意义**——这张卡的标称值从来没有达到过。

## 2.1 全部实验一览（统一以「单遍 online」为基准）

**读法：每一行的「累计改了什么」都是相对 ② 说的，不是相对上一行。** 这样任何一行都能独立看懂。

底座：`B=8, H=32, D=128, L=2048, BS=16, MAXB=128`，fp16 输入；PyTorch 参考实现 `8.362 ms`。
「占 221.4」= 实测带宽 ÷ 221.4 GB/s（本机实测天花板）；bench 打印的是 ÷272 标称值，两者不可混用。

|---|---|---|---|---|---|---|---|---|

| ② | **单遍 online（基准）** | `w7_paged_attn_单遍online.cu.bak` | — 基准本身：单 token 循环、m/denom 递推、grid 32 | 256.0 MiB | 1.8897 | 142.1 | 64.2% | 1.00× |

| ④ | 2 路 + split-L | `w7_paged_attn_split.cu` | + 2 路展开 + **split-L**（L 切 4 段，grid 32→128） | 256.0 + 2 MiB | 1.2483 | 215.1 | **97.2%** | 1.51× |

| ⑦ | 2 路 + KV + vec4 | `w8_paged_attn_int8kv_vec4.cu` | + 2 路展开 + K、V 都 int8 + **32 位 vec4 加载** | 130.1 MiB | 1.5503 | 88.0 | 39.7% | 1.22× |
| ⑧ | 2 路 + KV + split-L | `w8_paged_attn_int8kvsplit.cu` | + 2 路展开 + K、V 都 int8 + **split-L** | 130.1 + 2 MiB | 1.1223 | 121.3 | 54.8% | 1.68× |

三条对照关系（这才是这张表要表达的）：

1. **② → ③ → ④ 是同一方向上的递进**：先加 ILP（2 路），再加并行度（split-L），每步只改一处。
2. **⑤ 与 ⑥ 是一对干净的对照**：同为 2 路、同为 grid 32，**只差 V 的 dtype**。⑤ 87.8% → ⑥ 51.2%，直接证明「第二条流也变窄就亏 15%」。
3. **⑥ → ⑦ 只改「加载宽度」，⑥ → ⑧ 只改「并行度」**，两个分支都回不到 ⑤ 的水平（⑦ 更慢 29%，⑧ 只回收 7%）。→ 窄流的问题不能靠宽度或并行度单独解决。

## 4. 每一步为什么快

### 4.1 两遍 → 单遍（1.25×）

两遍版必须把 KV 读两遍：第一遍算分数找 max 和分母，第二遍才算加权和。**384 MiB 里多出的 128 MiB 就是 K 的第二遍**。

online softmax 把它消掉了：维护运行最大值 `m`、运行分母 `denom`、运行累加 `acc`，每来一个 token 就

```
m_new = max(m, s)
alpha = exp(m - m_new)        // 旧结果的缩放因子
denom = denom * alpha + p
acc   = acc * alpha + p * v
```

好处不只是少读 128 MiB，还因为**只在寄存器里迭代**，没有第二次全局扫描的启动开销。

### 4.2 单遍 → 2 路展开（1.25×）

单遍版每个 warp 每次迭代只有 **2 次 half load**（K 和 V 各一），而一次 load 的延迟是 400~600 个周期。
warp 里只有 2 个未完成的 load，硬件能重叠的请求太少 → 延迟没藏住，带宽只有 142 GB/s。

2 路展开后每次迭代有 **4 个独立的 load**（K0、V0、K1、V1），且它们之间没有依赖：

```cpp
s0 += q * k0[d];   s1 += q * k1[d];      // 两条点积交错
acc[k] = acc[k]*alpha + p0*v0[d] + p1*v1[d];
```

warp 级的等价写法是 **ILP-4**：4 个请求同时在飞，等第一个回来时其余三个已经排好队。
这一步把带宽从 142 推到 178 GB/s。

### 4.3 单链 → split-L（1.21×）

算一下并行度：`B*H = 256` 个 warp = **32 个 block**，而这张卡有 **24 个 SM**。

```
32 / 24 = 1.33 block/SM  →  每 SM 约 10.7 个 warp
SM 的 warp 上限是 64 →  只用了 17%
```

**不是带宽不够，是没有足够的 warp 去喂带宽。** 2 路展开把每 warp 的 ILP 提到了 4，但 warp 总数没变，一旦某个 warp 在等显存，SM 上就没有别的 warp 可以切。

split-L（= vLLM 的 flash-decoding / 分段归约）：

1. 每个 `(b,h)` 的 2048 次迭代切 4 段，交给 4 个 warp 并行；
2. 每段算完交回自己的 `(m_i, d_i, acc_i)`，**不归一化**；
3. 用一个 merge kernel 按 online softmax 的合并公式汇总：

```
M      = max_i m_i
alpha_i = exp(m_i - M)
d      = Σ d_i · alpha_i
acc[k] = Σ acc_i[k] · alpha_i
out    = acc / d
```

并行度 4 倍：`1024 warp = 128 block` → 5.33 block/SM，正好吃满寄存器允许的 5 个 block（`registers_per_thread=48` → 96 regs 上限不触发）。

**代价**：`partial_acc [4,8,32,128]` fp32 = 0.5 MiB 写 + 0.5 MiB 读 = **1 MiB**，只占总量 0.4%。
**语义关键**：split kernel 里绝不能除以 `denom`，否则每段的归一化基准不同，merge 时无法再校正。

## 5. 为什么停在这里

```
215.1 GB/s ÷ 221.4 GB/s（实测天花板）= 97.2%
```

只剩 **2.5%**。bench 报告的 79.1% 是拿 272 标称做的分母，而这张卡从未达到过 272——所有 kernel 的实测最高就是 221.4。

继续调 block 数、展开路数、`half2` 向量化，最多也只能拿回这 2.5%。
**要更快只有一个办法：少搬字节。**

## 6. 正确性验证

- 参考实现是 PyTorch 的**显式循环**（fp32 累加），不是 SDPA——PagedAttention decode 没有对应的 torch 算子，用 SDPA 会掩盖 `block_table` 映射的错误。
- 已验证：`L=2048`（偶数，主循环跑满）、`L=2049`（奇数，走收尾块）。
- **未验证**：`L < BS`（不足一个块，`t/BS` 与 `t%BS` 的边界）——这是欠账，写 README 时不能吹“全长度覆盖”。
- 收尾块曾经有 4 个 bug（`t/BS`、`t%BS`、`d += 32`、`acc[k]`），在 `kernels/CUDA错题本.md` 的 E-73/E-74 有记录。

## 7. INT8 KV cache（4 组实测：1 个正例 + 3 个反例）

> **共同基线（重要）**：本节四个 INT8 版本**全部**是「2 路展开的单遍 online softmax」（`t += 2`，一次吃两个 token）。整个 w7/w8 里唯一「一个 token 一次」的实现是 `w7_paged_attn_参考版.cu.bak`（1.9763 ms）。
> 所以这里的台阶**不是**「naive → 2 路 → split → 量化」的递进，而是固定基线之上的 **2×2 矩阵**：**加载宽度（单字节 / vec4）×并行度（grid 32 / 128）**。报告里必须写明这一点，否则会把台阶1 的 87.8% 误当成「K-only 的功劳」。

| 版本 | 流量 | ms | 实测带宽 | 占 221.4 天花板 |
|---|---|---|---|---|
| fp16 单链 2 路 | 256.0 MiB | 1.5084 | 178.1 GB/s | 80.4% |
| fp16 split-L | 256.0 MiB | 1.2483 | 215.1 GB/s | 97.2% |
| **INT8 K（台阶1）** | **193.1 MiB** | **1.0419** | **194.4 GB/s** | **87.8%** |
| INT8 K+V，单字节加载（台阶2 反例） | 130.1 MiB | **1.2032** | 113.4 GB/s | **51.2%** |
| INT8 K+V，单字节 + split-L（台阶4） | 130.1 MiB + 2 | **1.1223** | 121.3~122.5 GB/s | **55.3%** |

口径：bench 打印的百分比用标称 272 GB/s，本表「占 221.4」用实测天花板。表内数字取**同一进程内交替测量的中位数**（4 轮）——单次运行因冷启动与时钟状态可差 15%，不进结论。

做法（台阶1，只动 K，V/Q/out 仍是 fp16）：

- `k_q` = int8 `[NB,BS,H,D]`（128 → 64 MiB），`k_scale` = fp16 `[NB,BS,H]`（0.75 MiB），per-(token, head) 对称量化，`scale = max|x| / 127`。
- 反量化分两次：元素级 `(float)krow[d]`，以及归约后的 `s *= sc`（等价于把 scale 提到求和号外，每 token 只乘 1 次；放进内层就变成每元素乘 1 次，白吃 128 条乘法指令）。
- 误差：`max_abs = 9.77e-4`（参考值量级 0.64）、`max_rel = 9.5e-3`，远小于 1e-2 容差。

读数（台阶1）：流量 −24.6%，时间同比减少，带宽利用率与 fp16 版持平 —— **INT8 的收益是「字节数线性兑现」**，扇区利用率仍是 100%，没有付额外指令代价。

### 7.1 反例：只把 V 也换成 int8，反而慢 15%

台阶2 把 V 也量化成 int8，`scale` 折进权重（`pc = p * sv`，每元素仍是 1 次乘加），流量从 193.1 降到 130.1 MiB。**结果反而从 1.0419 ms 涨到 1.2032 ms**，利用率从 87.8% 掉到 51.2%。

原因：**两条流都退化成「每 lane 1 字节」，即每条 warp 访存指令只搬 32 B。**

- 台阶1：K 1 B/指令（32 B/warp）+ V 2 B/指令（64 B/warp），平均 48 B/指令 → 87.8%；
- 台阶2：K 1 B/指令 + V 1 B/指令，平均 32 B/指令 → 51.2%。

缺的不是字节总量，而是**每条指令带的字节数**（在飞字节数不够）。要吃满 DRAM，必须把 4 个 int8 打包成一次 `int` 加载（int8×4），让每条指令带 128 B。

> 记一条：**量化省字节，向量化保「每指令字节数」。只做前者不做后者，小维度（D=128）上会双输。**

### 7.2 反例 2：int8×4 向量化，更慢 29%

把 K/V 都改成「每 lane 一次读 4 个 int8」（`LDG.E` 32 位，32 lane 连续 = 128 B/指令）：

| 版本 | 流量 | ms | 实测带宽 | 占 221.4 |
|---|---|---|---|---|
| int8 K 单字节 | 193.1 MiB | 1.0419 | 194.4 GB/s | 87.8% |
| int8 K+V 单字节 | 130.1 MiB | 1.2032 | 113.4 GB/s | 51.2% |
| int8 K+V **vec4** | 130.1 MiB | **1.5503** | 88.0 GB/s | **32.4%** |

SASS 证据（排除了两个常见嫌疑人）：

```
int8kv   REG:56 LOCAL:0  134 条访存（86×LDG.E.U8 + 44×LDG.E.U16 + 4×LDG.E）
vec4     REG:56 LOCAL:0   47 条访存（41×LDG.E + 6×LDG.E.U16），总指令 1913 < 2617 行
```

- 不是寄存器溢出（两版都 56 reg、零 local）；
- 不是访存效率（32 位 `LDG.E`、32 lane 连续 = 128 B/指令，扇区 100% 利用）；
- 不是指令数（vec4 指令比老版少 27%）。

**真因是并行度，不是指令宽度。** `grid` 只有 32 个 block（24 SM → 1.33 block/SM ≈ 10 warp），能不能喂饱 DRAM 取决于**每个 warp 同时在飞的 load 条数**：

| | 每 token 每 lane 独立 load | 在飞槽位 |
|---|---|---|
| 单字节版 | K 4 + V 4 + q 4 = 12 条 | 12 |
| vec4 版 | K 1 + V 1 + q 2 = 4 条 | 4 |

每条变宽了，但条数从 12 掉到 4，warp 发完就只能等 DRAM —— 低占用率下，**"同时在飞的请求数"比"每条指令带多少字节"更重要**。次要负分：写回改成 `lane*4 + i`，每个 store 跨 256 B 只用 64 B。

> 记一条：**向量化提高的是"每指令字节数"，代价是"指令条数"。只有占用率足够高（warps 多）时前者才净赚；本项目 grid 仅 32 block，先补并行度。**

### 7.3 台阶4：并行度 ×4 之后，上面的结论被证伪

§7.2 把慢归因为「grid 只有 32 个 block、在飞条数不够」。台阶4 就测这一条：**其余全部不动，只把 L 切成 4 段给 4 个 warp（grid 32 → 128），单字节 load 保留**，最后 merge。

| 版本 | 流量 | ms | 实测带宽 | 占 221.4 |
|---|---|---|---|---|
| int8 K 单字节，grid 32 | 193.1 MiB | 1.0419 | 194.4 GB/s | **87.8%** |
| int8 K+V 单字节，grid 32 | 130.1 MiB | 1.2032 | 113.4 GB/s | 51.2% |
| **int8 K+V 单字节，grid 128** | 130.1 MiB + 2 | **1.1223** | 121.3 GB/s | **55.3%** |
| int8 K+V vec4，grid 32 | 130.1 MiB | 1.5503 | 88.0 GB/s | 32.4% |

三次实测 `1.0281 / 1.1339 / 1.1223`，取**中位数 1.1223**；单次跨度 10%，冷启动那个值不进结论。

读法：

- warp 数 ×4，带宽只从 113.4 涨到 121.3（**+7%**），离 87.8% 还差 30 个百分点；
- 如果瓶颈真是"warp 太少盖不住延迟"，这一格应该跳到 85%+ —— **它没有**。

所以 §7.2 的结论要撤回。正确的解释是两条叠加：

1. **窄指令的条数本身就是瓶颈**：两条流都退化成 32 B/指令后，一个 token 要发 16 条 LDG（fp16 只要 8 条），发射口被占满。此时加 warp 只是让更多 warp 去排同一个发射口，**在飞字节数不变**。
2. **台阶1 为什么能到 87.8%**：它只有 K 变窄，V 仍是 fp16（64 B/指令），宽窄两种指令混着发，才维持住在飞字节数。

> **修正记录**：§7.2 写的"真因是并行度，不是指令宽度"是**错的**，已被台阶4 证伪。改记为：**窄指令条数本身是天花板，单靠加并行度救不回来。**

### 7.4 结论边界

INT8 路线**到此为止**，不再往下做。理由是上面三组实测已经把问题说清楚了：

- 只量化 K（⑤）是唯一赢的组合：−24.6% 流量、87.8% 带宽、`1.0419 ms`；
- 再往 K+V 走（⑥⑦⑧）三条路都没回来：换字节宽度更慢、加并行度只回收 7%；
- 剩下的组合（K 量化 + split-L、KV + vec4 + split-L）**没有实现，也没有数据**，本报告不对它们下任何结论。

如果以后还想往下试，只有一条值得做：把 ⑤ 的 split-L 补上再测一次，验证「单向窄流 + 高并行度」是否能到 96%。**这一条没有实现、没有数据，不在本报告范围内。** `1.0419 ms` 就是这条线的最终数字。

## 9. 面试能讲的三点

1. **为什么 decode 是带宽题**：AI=32 vs 拐点 240，算力闲着，瓶颈是 256 MiB 的 KV 读。
2. **为什么 2 路展开有用而 4 路没继续**：ILP 补的是“单 warp 内请求数”，split-L 补的是“warp 总数”；前者天花板是寄存器，后者天花板是 SM 数量。到 97% 实测带宽后两者都没意义了。
3. **split-L 的坑在归一化时机**：每段用各自的 `m_i` 算出的 `d_i` 和 `acc_i` 是不同基准的，必须在 merge 时用 `exp(m_i - M)` 校正；提前归一化就无法还原。
4. **INT8 省的是搬运不是算力**：decode 阶段算力闲置，int8 的全部价值是把 K 的 128 MiB 砍到 64 MiB；实现上仍是「读 int8 → 转 float → fp32 累加」，真正的整数算力要等 dp4a。scale 必须乘在归约之后（`Σ q·(sc·k) = sc·Σ q·k`），否则每元素多一条乘法。
