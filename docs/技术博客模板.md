拐点算术强度是这篇文章的关键数字，它等于"峰值算力 ÷ 峰值带宽"：

> **算术强度低于这个值的算子，瓶颈在带宽而不在算力。**

而 LayerNorm / Softmax / 标准 Attention 的算术强度只有 【?】~【?】。
**也就是说：在这张卡上，我要写的绝大多数算子都是 memory-bound。**
优化的方向从一开始就确定了：**减少 HBM 往返，而不是提高算力利用率。**

## 二、三个测量上的坑（比优化本身更重要）

<!-- 这一节是你的差异化。大多数人只写"我优化了什么"，不写"我怎么保证测的是对的"。 -->

### 坑 1：CUDA 是异步的，`time.time()` 测出来是错的

```python
start = time.time()
out = model(x)          # 只是把 kernel 扔进队列就返回了
print(time.time() - start)   # 测的是"CPU 发命令的时间"
```

改成 CUDA event，并且只在每轮末尾同步。**另外必须预热** —— 前几次调用包含
JIT、autotune 和 GPU 频率爬升。

### 坑 2：不冲刷 L2，测到的是缓存速度

反复测同一份数据会命中 L2。我一开始算出的"有效带宽"超过了显存理论带宽，
才发现这个问题。修法是在每次计时前往一块 256MB 的缓冲区写入，把 L2 挤干净。

**如果你算出带宽超过峰值，那不是你优化得好，是你的测量错了。**

### 坑 3：峰值算力不能用 `nvidia-smi` 的频率

`nvidia-smi` 报告 `Max Clocks: SM = 3105 MHz`，厂商标称 boost 是 2370 MHz。
**两个都不能用。**

- 3105 MHz 是硬件上限，永远跑不到
- 2370 MHz 是"最好情况下"，笔记本卡受功耗墙和散热限制，持续频率更低

我用自写的采样脚本在跑 benchmark 时记录 SM 时钟，取中位数
**【?】MHz**，再按 `CUDA核心数 × 2 × 频率 × 4` 重算峰值算力。

> **这一步直接改变结论**：用错频率，所有"算力利用率"都是错的，
> 而且错得很隐蔽 —— 数字看起来正常，只是系统性偏高或偏低。

## 四、第二次优化：FlashAttention

### 先证明问题存在

标准 attention 会实体化一个 S×S 的分数矩阵。序列长度 4096、8 个 head 时，
这个中间矩阵光显存就要 **【?】MB**，而它读写 HBM 的流量占了总流量的 **【?】%**。

我用 Roofline 算了它的算术强度：**【?】** FLOPs/Byte，远低于拐点 【?】。
**结论：标准 attention 是 memory-bound，瓶颈就是这个中间矩阵。**

### 再看解法

FlashAttention 的做法是不实体化中间矩阵，分块计算并在线累积。
**注意：它没有减少任何计算量**（FLOPs 完全相同），减少的是 HBM 流量：

| | FLOPs | HBM 访存 | 算术强度 | 瓶颈 |
|---|---|---|---|---|
| 标准实现 | 【?】 G | 【?】 MB | 【?】 | memory-bound |
| FlashAttention | 【?】 G | 【?】 MB | 【?】 | **compute-bound** |

流量降低 **【?】x** 之后，算术强度越过拐点，**瓶颈从带宽转移到了算力**。
这就是"用重算换访存"的准确含义。

## 六、结论

1. 在带宽受限的卡上，**先判断 bound 类型再动手**，比盲目调参有效得多
2. **测量方法错了，优化就是白做。** 三个坑里有两个是测量问题
3. FlashAttention 的本质是改变瓶颈类型，不是减少计算
4. 8GB 显存不是劣势 —— 它逼我正面处理显存问题，而这正是端侧部署的日常
