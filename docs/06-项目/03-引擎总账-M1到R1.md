# mini 推理引擎总账：M1 → R1 做了什么

> 一句话：**把 `kernels/` 里那些吃 `block_table` 的单算子，接进一个真的会分配块、真会调度、真能出数的引擎里。**
>
> 每个台阶一条判据，过不了不进下一步。所有数字都在 RTX 4060 Laptop（8 GB, 24 SM）上实测，模型 gpt2-124M。
> 细节实现见 `engines/README.md`，本节只是**总账 + 面试口径**。

---

## 1. 一页总表

| 台阶 | 做了什么 | 判据 | 结果 | 回答的面试问题 |
|---|---|---|---|---|
| **M1** | 纯 PyTorch 手写 greedy 循环，每步重算整段 | 20 token 与 HF `generate` 逐位一致 | ✅ 一致；fp32 **730.4 ms** / fp16 **325.7 ms**；峰值 496 MB | 「你懂不懂 KV cache 之前长什么样」 |
| **M2** | 手写 KV cache，不再重算历史 | 逐位一致 + 每步耗时不再随 S 线性增长 | ✅ 5/5 轮一致；稳态单步 **18.57 → 4.89 ms（3.79×）**；总耗时 **355.0 → 110.1 ms（3.23×）**；峰值 704.5 MB | 「KV cache 到底省了什么」 |
| **M3a** | 分页 KV 池 + `block_table`（attention 仍 HF） | 8 步 × 12 层 K/V 与 `DynamicCache` 逐位一致 | ✅ 全一致；池 **72.0 MiB**（容量 1024 token）；19 token = **2 块**，利用率 2% | 「PagedAttention 的块表怎么用」 |
| **M3b-1** | cache 全自己管：池取 K/V + 自己算 attention（PyTorch） | 8 步 greedy token 与 M2 完全一致 | ✅ `[1849, 464, 22482, 547, 257, 1402, 11, 475]` 一致 | 「你换掉 HF 的实现，凭什么说对」 |
| **M3b-2** | attention 换成自研 `paged_attn_split` kernel（fp16） | token ≥19/20 + 单步对比 SDPA | ✅ 20/20；端到端 **0.93×**（S=12，慢 7%） | 「kernel 接进系统还能对齐吗」 |
| **M4** | 分页 KV 读写从 Python 逐 token 循环改成索引 kernel | TTFT 下降；token 20/20 | ✅ **TTFT 120.13 → 7.37 ms（16.3×）**；吞吐 **94.4 → 204.2 tok/s**；总 212 → **96.1 ms** | 「端到端慢了，瓶颈在哪」 |
| **M5** | continuous batching（8 条不等长请求共用池） | B=1 逐位一致 + 自比 8/8 + 无泄漏 | ✅ **4.06×**（861.4 → 211.9 ms，168 → 27 次 forward）；块泄漏 0；峰值 17/256 | 「batching 你做过吗，加速多少」 |

## 2. 每一步的「为什么」和「怎么验」

### M1：先证明你懂最笨的做法
- **为什么**：不会写 naive，就说不清 KV cache 省了什么。M1 是基线，也是**正确性的第一把尺子**（HF 的 `generate` 是裁判）。
- **怎么验**：`torch.equal(my_tokens, hf_tokens)`，20 个 token 必须逐个相同。
- **看到了什么**：每步越来越慢（第 1 步 S=6、第 20 步 S=26），累计做功 O(S²)——这就是要给 M2 消掉的东西。

### M2：KV cache 的收益要分成两个数报
- **为什么**：KV cache 消掉的是「每步重算整个前缀」，越到后面越省；但第 1 步的 prefill 两条路都要吃。
- **口径（重要）**：
  - **稳态单步 3.79×** ← 说「KV cache 的收益」用这个
  - **总耗时 3.23×** ← 说「20 步端到端」用这个
  - 混用会被追问「到底是 3.79 还是 3.23」。
- **测量协议（可复现）**：交替测 A/B（抵消频率/温度漂移）→ 丢第 1 轮（首次要建 cache、扩分配器，实测是稳态的 15 倍）→ 剔 >2× 中位数的样本 → 取中位数。脚本自带 `assert` 每轮逐位相同。

### M3a：分页语义的正确性，只能靠逐位比
- **为什么**：真实引擎里 KV 不连续——`block_table[seq, page] → 物理块号`，块随请求增长、用完回收。这一步只验**索引对不对**。
- **怎么验**：每写一个 token 就 gather 回来，和 `DynamicCache` 的 K/V 比 `torch.equal`。8 步 × 12 层全过。
- **看到了什么**：池 72 MiB 只用了 2 块（19 token），**利用率 2%**——这就是后面 M5 存在的理由（单请求分页几乎没收益）。

### M3b-1：把「谁管 cache」换掉
- **为什么**：M3a 是「旁边抄一份」，M3b-1 是「只留我们这一份」——HF 不再拥有 cache，K/V 从池里取。
- **两个不报错但结果错的坑**（都记进错题本了）：
  1. **闭包晚绑定**：`for layer_idx: def patched(...)` 中 12 个函数全看到 `layer_idx=11` → 工厂函数绑参数。
  2. **没传 `position_ids`**：自己管 cache 后 HF 认为无历史，位置每步从 0 算 → 第一个 token 对、后面全崩（`[1849, 11, 11, ...]`）。

### M3b-2：kernel 接进系统，先要「对得上」
- **为什么**：`kernels/w7_paged_attn_split.cu` 吃 `block_table`/`context_lens`，在 bench 里这些是 `randn` 假数据；这一步第一次让**真块表**喂进去。
- **判据是「对得上」不是「更快」**：`engines/README.md` 当时就写了「不追求比 HF 快多少」。
- **结果 0.93×**：慢 7%，来源是每层一次通用 kernel 调用 + paged 寻址。**不能说「比 HF 快」**。

### M4：瓶颈不在字节数，在调用次数
- **诊断**：prompt S=441 时 TTFT 120 ms，HF 只有 7–9 ms。decode 几乎持平（4.73 vs 4.30）⇒ 问题全在 prefill 把 KV 写进池。
- **定位**：`m3_paged_attn.py:68 for j in range(s_new)` × 12 层 = **5292 次调用**、10 584 次 slice-assign；gather 同量级。111 ms ÷ 15 876 ≈ **7 µs/次** ⇒ 是**调用次数**，不是拷贝慢（32 MB / 221 GB/s 只要 0.145 ms，差 767 倍）。
- **改法（不是写 kernel，是换 API 的组合方式）**：池里一层 `[64,16,12,64]` 摊平就是 `[1024,12,64]`，**一个 token 一行** ⇒ 写入 = 一次行索引 scatter（`index_copy_`），读取 = 一次 `index_select`。索引与层无关，只在 layer 0 算一次。
- **结果**：TTFT 120.13 → **7.37 ms（16.3×）**，吞吐 94.4 → **204.2 tok/s**，token 20/20。**TTFT 已快于 HF（7.37 vs 7.33–7.87）**，总耗时仍慢 11%（96.1 vs 86.4）——因为 decode 每步还慢 0.52 ms。

### M5：batching 的收益要证明「不是靠运气」
- **做了什么**：8 条不等长请求共用一块池，每步拼成 `[B,1]` 一次 forward，各自 argmax；跑完的请求让出块。
- **结果**：串行 861.4 ms（168 次 forward）→ 批量 **211.9 ms（27 次 forward）= 4.06×**；块泄漏 0。
- **正确性怎么讲（关键）**：
  1. 每条路径自比 **8/8**（可复现）
  2. `MAX_BATCH=1`（走批量代码路径、形状同串行）→ **8/8 逐位一致**（索引/块表/寻址都对）
  3. `MAX_BATCH=8` → **7/8**，1 条在第 13 步翻转一次近义 token（3665→1588），随后收敛 ⇒ 是 fp16 累加顺序变了，不是逻辑错
- **为什么这样定判据**：如果一开始就写「8 条必须逐位一致」，那是在掩盖问题；如果只报 4.06×，那是没验。**先证明可复现，再证明形状无关，最后披露 batch 维度的差异。**

### R1：从「Python 函数」变成「torch 算子」
- **为什么**：`load_inline` 只暴露一个 Python 函数 `mod.forward(...)`；注册后是 `torch.ops.aigpu.flash_attn(...)`，才能被 `torch.compile` 捕获、在 profiler 里有名字、能挂 autograd、能替换 `F.scaled_dot_product_attention`。
- **四层**：`custom_op`（schema）→ CUDA 实现 → `register_fake`（图阶段）→ `register_autograd`（反向）。
- **四条判据**：数值 vs SDPA < 2e-3 / `torch.compile(fullgraph=True)` 不 graph break / profiler 里出现算子名 / 替换 SDPA 后引擎仍跑对。

## 3. 三条数字纪律（写简历、面试都按这个）

| 纪律 | 反例 | 正确说法 |
|---|---|---|
| **稳态与总耗时不混报** | 「KV cache 快 3.23×」（那是总耗时） | 「稳态单步 3.79×，20 步端到端 3.23×」 |
| **自比与对 HF 比不混报** | 「TTFT 快 16.3×」（那是 M4 前后自比） | 「M4 内部 16.3×；与 HF 比 TTFT 持平（7.37 vs 7.33–7.87），总耗时慢 11%」 |
| **逐位与一致率不混报** | 「batching 完全一致」 | 「B=1 逐位一致；B=8 时 7/8，差异来自 fp16 累加顺序」 |

## 4. 还没做的（诚实清单）

| 项 | 为什么没做 | 值多少 |
|---|---|---|
| **B′：prefill 只写不读**（真实引擎不 gather 回来算） | TTFT 已压到 HF 以下，只值 0.3–0.5 ms | 小 |
| **真 continuous batching（请求动态到达）** | 现在 8 条同时 admit，更接近静态 batch | 中（要加到达时间/准入策略） |
| **prefix caching + 引用计数** | 需要 hash 共享前缀 + ref-count 回收 | 中（vLLM 的核心卖点之一） |
| **采样（top-k / top-p / temperature）** | 现在只有 argmax | 小（1 h） |
| **OpenAI 兼容 API server** | 没写 | 小（半天，但是「像个产品」的门面） |
| **CUDA Graph 捕获 decode** | 每步 12 层 pybind，理论上可消 | 中（decode 每步 0.52 ms 的差距来源） |
| **多请求公平性 / P99 延迟** | 单请求、8 条固定 | 大（要真实并发负载才有意义） |

**这些不做的理由已写进 `docs/06-项目/01-mini推理引擎.md` §13，面试被问到时说「知道但按优先级砍了」，不要说「没想到」。**

## 5. 面试稿

### 30 秒版

> 「`kernels/` 里我写了 PagedAttention 的 decode kernel，但它吃的 `block_table` 在 bench 里是假数据。所以我写了个 mini 引擎补上生产者那一半：分页 KV 池、块分配、continuous batching。gpt2-124M 上，KV cache 稳态 3.79×，分页 KV 读写改成索引 kernel 后 TTFT 从 120 ms 降到 7.4 ms，8 条并发吞吐 4.06×，输出和 HF 逐位对齐。」

### 2 分钟版（追问时展开）

1. **为什么做**：单算子证明不了「会用」；引擎补的是「谁生产 block_table」。
2. **正确性怎么保证**：每一层都有裁判——M1/M2 对 HF `generate`，M3a 对 `DynamicCache` 逐位，M3b 对 M2，M5 对串行自比。
3. **最硬的一个发现**：M4 的 111 ms 不是带宽问题，是 **15 876 次 Python 调用**（7 µs/次）；数据只有 32 MB，带宽只要 0.145 ms。改成 `index_copy_`/`index_select` 后 24 次调用，TTFT 降 16.3×。
4. **batching 的正确性怎么讲**：先证可复现（8/8）、再证形状无关（B=1 逐位）、最后披露 B=8 的 7/8 是 fp16 累加顺序。
5. **还差什么**：prefill 只写不读、prefix caching、采样、API server、CUDA Graph。
