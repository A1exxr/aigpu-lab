# FA 前向三版对照（w12 标量 → w12b wmma → w12c mma.sync）

> 目的：给 v3（TMA + wgmma）留一个**数值相同、只是快慢不同**的 v2 基线。
> 判据：causal + GQA，B=2 / H=8 / Hkv=2 / D=64，fp16 输入、fp32 累加。
> 日期：2026-11-15 ~ 11-16（14 天计划的 D1–D3）。

## 一句话结论

同一份算法换三种「数据放在哪」，从 2.61 涨到 5.10 TFLOPS（1.96×）；
真正起作用的**不是用上 Tensor Core**（w12b 用上了反而更慢），而是
**Acc 和 P 有没有被搬进/搬出共享内存**。

## 数字

| 版本 | 结构 | S=512 | S=1024 | 占 SDPA（S=1024） |
|---|---|---|---|---|
| w12 标量 | 无 TC，1 LDS : 1 FMA | 0.268 ms / 2.01 TFLOPS | 0.825 ms / 2.61 | 0.21× |
| w12b wmma | TC，但 Acc 过 smem | — / 1.53 | — / 2.01 | 0.16× |
| **w12c mma.sync** | TC，Acc 与 P 全在寄存器 | **0.115 ms / 4.66** | **0.422 ms / 5.10** | **0.44×** |

SDPA 同 shape 两次跑分别是 9.57 / 12.68 TFLOPS 和 6.99 / 11.62 TFLOPS
（**抖动 8–48%**，见下面「口径」一节）。

正确性（三档都 PASS）：

| S | max&#124;diff&#124; | 判据 |
|---|---|---|
| 512 | 3.644e-04 | ≤ 3e-3 |
| 125 | 4.944e-04 | ≤ 3e-3（尾块用例，S 除不尽 64） |
| 1024 | 5.429e-04 | ≤ 3e-3 |

## 每个数为什么是这个数

**w12 标量 2.61 TFLOPS = 自己天花板 4.08 的 64%。**
FFMA 峰值 = 24 SM × 128 lane × 2 × 2.655 GHz ≈ 16.3 TFLOPS；
代码里每条 LDS 配一条 FMA（1:1），而 smem 的 LDS 吞吐是 32 lane/clk、
FFMA 是 128 lane/clk ⇒ 天花板 = 16.3 × 32/128 ≈ **4.08**。
所以标量版不是「没优化好」，是**指令配比锁死了上限**。

**w12b wmma 2.01 TFLOPS：用上 TC 反而更慢。**
两个原因都是 API 强加的：
1. `wmma` 没有「accumulator → matrix_a」的转换，P 必须落 smem 再装回 A 片段
   ⇒ 每 tile 16 KB 读写；
2. `Acc` 也只能过 smem，再 16 KB。
加上 smem 吃到 37.6 KB ⇒ 每 SM 只 2 个 block ⇒ 占用率 **16%**。

**w12c mma.sync 5.10 TFLOPS：2.5× 全部来自「不搬」。**
1. **Acc 全程留寄存器**（`sc[4][4]`），softmax 与 α 缩放都在寄存器上做；
2. **P 不过 smem**：`mma.sync` 的 C 布局与 A 布局前四格完全相同
   （`c0c1=P[g][2t..]` / `a0a1=P[g][2t..]`，`c2c3=a2a3` 同理），
   `pack2` 打包成 `unsigned` 直接当 A 用，**零 shuffle**；
3. smem 只剩 Qs+Ks+Vs = **16 KB**，95 寄存器 0 spill ⇒ 每 SM 5 个 block
   ⇒ 占用率 **41.7%**（5 × 4 warp / 48）。

SASS 对账（`cuobjdump -sass` 计数）：`HMMA 32`（16 QK + 16 PV）、
`LDSM 36`（4 Q + 16 K + 16 V）、`MUFU 27`（exp）、`95 registers / 0 spill`。

## 两个 bug（数值全对才暴露的那类）

**① 尾块错位 3 行（w12b，S=125 时 FAIL 7.1e-02）。**
`load_matrix_sync` 只接受起始指针，所以把指针夹到 `S-16` 之后，
fragment 装的是 Q 的 109…124 行；但 `store_matrix_sync` 写的是
`Ss + (warp_id*16)*TILE_N`，用的是 **warp 位置**。
两边错位 3 行 ⇒ 全局行 112…127 拿到了 109…121 的分数。
错的是「夹住指针 ≠ 夹住行」。修法：不夹指针，改夹**块起点**
`row_base = min(blockIdx.x*TILE_M, S - TILE_M)`（要求 S ≥ 64）。
S=512 能整除 64，所以这个 bug 只在 S=125 暴露。

**② `ldmatrix` 的地址必须是 shared state space。**
漏 `__cvta_generic_to_shared` 传进去的是 generic 地址，运行期报非法访问；
另外要求 **16 B 对齐**。

## 口径（报数前必须写清的三条）

1. **TFLOPS 的 FLOPs 要减半**：`2·B·H·S·(S+1)·D`。忘了减半会虚高
   `2S/(S+1)` ≈ 2 倍（S=1024），这个错会让「0.39× SDPA」看起来像 0.78×。
2. **别用 ratio 当结论**。我们两次跑 0.431 → 0.422 ms（2% 抖动），
   SDPA 同 shape 却从 12.68 掉到 11.62（8%），S=512 更是 10.39 → 6.99（48%）。
   所以「0.39× → 0.44×」主要是 **SDPA 侧变慢**，我们没变快。
   对外报**绝对时间和 TFLOPS**，ratio 注明是几次、什么时候测的。
3. **小 shape 会骗人**：SDPA 自己在这个 shape 也只有 19% 峰值（12.68 / 65.2），
   跨实现比较必须同 shape，并同时报「占峰值比」。

## 还差什么（按预期收益排序）

| 没做 | 为什么值得做 | 预期 |
|---|---|---|
| `cp.async` 双缓冲 | K/V 全局加载延迟现在完全暴露在 `__syncthreads` 两侧 | 6–7 TFLOPS |
| TILE_M 64 → 128（8 warp） | 一个 warp 只干 16 行 Q，K/V tile 复用率减半 | 8–9 TFLOPS |
| split-K（长序列） | S 很长时 grid 只有 B·H 个 block，喂不饱 24 SM | 看 shape |

但这三件**都是 v3 要重写的东西**（TMA 天生带流水、wgmma 天生吃大 tile），
在这里做等于做两遍。所以 v2 停在 5.10，直接进 v3。

## 面试口径（三句话）

1. 「手写了 FA2 前向三版：标量版 2.61 TFLOPS，wmma 版反而掉到 2.01，
   mma.sync 版 5.10（S=1024，causal+GQA，0.44× SDPA）。」
2. 「wmma 慢是因为它不允许 accumulator 直接当 matrix_a 用，P 和 Acc
   每 tile 各搬 16 KB 共享内存，占用率只有 16%；mma.sync 把两者都留在寄存器，
   P 的 C 布局和 A 布局前四格完全一致，打包即用，零 shuffle。」
3. 「剩下的 2.6 倍不在数学上，在流水和 tile 复用上——那就是 v3 用
   TMA + wgmma 要解决的，所以我没有在 v2 上继续磨。」
