### Q3 合并访存 —— 方向完全正确，只需补数字

你答：「合并访存是因为 cuda 底层读写操作都是 32 字节为的单位，所以数据要放得临近一点，合并访存就可以减少访存次数，优化访存效率」——**判断对，术语和数字补全如下**：

```
一个 warp = 32 个线程
每个线程读 4 字节（float）
32 × 4 = 128 字节 = 恰好一条 cache line
```

- **cache line = 128 字节**，由 **4 个 sector** 组成，**每个 sector = 32 字节** ← 你说的「32 字节」就是这个
- 显存事务以 **sector** 为最小单位
- 术语：相邻线程访问相邻地址 = **coalesced access（合并访存）**
- ✅ `out[i] = x[i]` 是合并的
- ❌ `out[i] = x[i * 2]` 不是：32 个线程散在 32 条 cache line 上 → 要 32 次事务 → 有效带宽掉到 1/32

### 四个旋钮

| 旋钮 | 本质 | 调大的好处 | 调大的代价 |
|---|---|---|---|
| `Block_m` | 一个 program 负责多少行 Q | Q 只读一次、输出只写一次、grid 变小 | 中间量 `s` 是 `Block_m×Block_n` 的 **fp32，占寄存器** → 溢出、occupancy 掉 |
| `Block_n` | 每轮从 K/V 取多少行 | 循环次数↓（16→8 轮）、`tl.dot` 的 K 维变长 → Tensor Core 每次算得更满 | 每级流水的 K/V buffer 变大（×stages）→ 共享内存吃紧 |
| `num_warps` | 一个 program 用几个 warp 切 tile | 单 program 内并行度↑ | tile 被切碎，每 warp 分到的 mma 变小，喂不饱 Tensor Core 最小 16×8×16 粒度 |
| `num_stages` | 预取几块 K/V 做软件流水 | 第 2 块的**加载**与第 1 块的**计算**重叠 → 藏住访存延迟 | 共享内存 ×stages → occupancy↓ |

### 四条铁律（带实测数字，w5：B4 H8 S1024 D64）

1. **`num_warps ≈ Block_m / 16`**。M64 就该 4；给它 8 个 → 每 warp 8 行 < 16 → **0.492 → 0.872 ms**（慢 77%）。warp 不是越多越好，要和 tile 匹配。
2. **`Block_n` 加到 128 通常划算**：循环 16→8 轮、dot 的 K 维翻倍 → 0.580 → 0.436 ms（同 s1）。
3. **`num_stages=2` 多数情况最优，3 不一定好**：0.436(s1) → 0.409(s2) → 0.478(s3)。stages 每加一级多占一份共享内存，occupancy 掉下来会反超收益。
4. **`Block_m` 只在「K/V 重读是瓶颈」时才有用**。这里是 compute-bound，M128 反而 0.518（比 M64 的 0.473 慢）——`s` 变大（128×64 fp32）压垮寄存器。

### 怎么用（流程）

```
1. 判瓶颈（带宽% vs 算力%）
2. 一维扫描：固定其他三个，只动一个，看方向
3. 组合最优（如 N128 + s2）
4. 复核：连跑 3 次取中位数，别信单次
```

**第 4 步不是形式主义**：这台机器单次波动能到 16%（同一配置我测到过 0.409 和 0.474）。

### 自测（2026-10-22）

**Q1 `Block_n` 改 256 会怎样？** 🟡
- 对：循环 8→4 轮 ✓、K 维变长 ✓、共享内存不够 ✓
- 错：说「取 K/V 更快了」——**总字节数不变**（还是整个 K/V 过一遍），快的是**循环开销**和 **Tensor Core 单次效率**。

**Q2 为什么 `w8` 在 `M128/N128` 没 `M64/N64` 那么惨？** 🟡 原理对、答非所问
- 你答的是「warp 越多 / tile 越小 → 切碎」，方向对。
- 但问题问的是**为什么同一个 w8 在两个 tile 上表现不同**：答案在**每 warp 的行数**——
  `M64/N64` 配 8 warp → 每 warp **8 行** < mma 最小 m=16 → 完全喂不饱；
  `M128/N128` 配 8 warp → 每 warp **16 行** = 刚好够 mma 粒度 → 只是慢，不是崩。
- 一句话：**看的是「每 warp 的行数」，不是「warp 的数量」。**

### E-87（2026-10-28，🔴 不会推）store 的地址跨度怎么算 → 扇区效率

**题面**（本项目 `w8_paged_attn_int8kv_vec4.cu` 的写回）：`out` 是 fp16，4 个元素打包写了 4 条 store：

```cpp
for (int i = 0; i < 4; ++i)
    out[(base + lane * 4 + i)] = __float2half(o4[i]);   // o4 是 float4
```

问三件：① 一条 store 指令在 warp 内的地址跨度是多少字节；② 它落在几个 32 B 的 sector 里；
③ 扇区效率多少；④ 既然只有 25%，为什么本项目里影响很小。

**当时的回答**：跨度答「32×4×2 B = 256 B」（对了一半，见下）、每个 store 只覆盖 1 个 sector（错）、
效率「不知道」。

**正解**

1. **只看一条指令**（`i` 固定）。lane `L` 的地址 = `base + L*4 + i`，相邻 lane 差 **4 个元素 = 8 B**
   → 32 条 lane 摊开是 `0, 8, 16, …, 248` → 用到的地址区间是 `248 + 2 = 250 B`，
   即 **8 个 sector（8 × 32 = 256 B）**。
   注意：256 B 是"触达的范围"，不是"一条 lane 搬的量"。
2. 一条 store 真正有用的字节 = 32 lane × 2 B = **64 B**。
3. **扇区效率 = 有用 / 触达 = 64 / 256 = 25%**（每个 sector 32 B 里只用 8 B）。
4. **为什么本项目影响小**：`i = 0..3` 四条指令落在**同一批 8 个 sector** 上，
   L1 第二次就命中了；而 `out` 只有 1 MiB，DRAM 层面几乎不重复取。
   一旦 `out` 大到几十 MiB、且写占比升高，这 25% 就会变成主因。

**一句话判据**
> 一条指令：跨度 = (lane 数 − 1) × 相邻 lane 的字节差；sector 数 = ⌈跨度 / 32⌉；
> 效率 = 有用字节 / (sector 数 × 32)。展开的多条指令若落在同一批 sector，L1 会合并，别重复扣。

**E-80（新增，🔴）** 低占用率下"指令数变少反而变慢"的机制：
- 打满带宽的条件是 **在飞字节 ≥ 带宽 × 延迟**；

#### ❌ E-88（新，🔴）扇区利用率：要用「相邻 lane 间距」，不是「首尾跨度」

- **当时算的**：lane0 与 lane31 差 `31*64*2 = 3968 B`，利用率 `64/3968 = 1.6%`（改成 16 B 后 12.9%）。
- **正确**：
  - 相邻 lane 间距 = `D × 2 = 64 × 2 = 128 B`（lane 之间 j 只 +1，地址只加一行 `D`）；
  - 硬件按 **32 B 扇区**取：每 lane 要 2 B，也得搬 32 B → 32 lane × 32 B = **1024 B**；
  - 用到 = 32 × 2 = **64 B** → `64 / 1024 = 6.25%`。
- **(b) 每 lane 读 16 B**：16 B 仍在一个 32 B 扇区内 → 用 512 B / 搬 1024 B = **50%**。
- **(c) 修的方向**：让 warp 内地址**沿 d 连续**（换映射：warp-per-j、lane 沿 d），同时每 lane 多读几个元素。
- **为什么错**：拿“跨度”当“间距”，分母用了整段的字节数而不是“扇区数 × 32 B”。这和 E-15（用错分母）、E-20 是同一族错误。

#### ❌ E-89（新，🟡）split-L merge 必须最后除以全局分母

- **漏的**：`out[k] = acc[k] / d`（`d` 是合并后的全局分母）。
- 三个公式完整版：
  ```cpp
  M = max_i m_i;
  d = Σ_i d_i * exp(m_i - M);
  acc[k] = Σ_i acc_i[k] * exp(m_i - M);
  out[k] = acc[k] / d;        // ← 这行漏了
  ```
- 索引是 `partial_acc[i][bh][k]`，不是 `partial_acc[k]`；`partial_m[i]` 是数组不是函数。
- **为什么重要**：少了这一步，输出是“加权和”而不是“加权平均”，数值会大 O(d) 倍（d 量级 ~S），`max_abs` 直接爆表。

#### ❌ E-90（新，🟡）假带宽：分子是「名义字节数」，L2 命中时它会虚高

- `--no-flush-l2` 时 gelu 报 512 GB/s，不是卡变强了，而是**数据已在 L2 里**，DRAM 没怎么动；
- 但代码里的分子 = `bytes_elementwise(shape, dtype, 1, 1)`（按“应该读多少 DRAM 字节”算的），分母 = 实测时间 → **分子虚高、时间变小 → 假高**；
- 判定：`> 峰值(272)` 就一定是假的；`flush 256 MiB` 之后 221 GB/s 才是真值。
- 一句话：**带宽 = 真实 DRAM 字节 / 时间；L2 命中让“真实”两个字失效。**

#### ❌ E-91（新，🔴）half 的寄存器单位：2 个 half 装 1 个 32 位寄存器

- 错的算法：`cols=8192、256 线程 → 每线程 32 个元素 → sreg 32 个寄存器 + dyreg 32 个 = 64 个`
- 正确的算法：**half 是 2 字节，2 个 half 打进 1 个 32 位寄存器**
  - `sreg[32]` = 32 个 half = **16 个寄存器**；两个数组共 **32 个寄存器**
- 判据（算 occupancy，不是算“够不够”）：
  ```
  每线程寄存器数 R = 数组 + ~15（下标/基址/中间值）
  每 SM 寄存器总数 65536
  可行 block 数 = 65536 / (R * 256)     // 256 线程/block
  要 6 个 block 驻留 → R <= 42
  ```
  本例 R ≈ 32 + 15 = 47 → 只能 5 个 block（不是“溢出”，是**占用率掉**）。**> 255/线程才是真溢出到 local。**
- **为什么错**：把“元素个数”当“寄存器个数”，漏了 half 的打包。同族错误：E-15（用错分母）、E-83（单位换算）。

#### ❌ E-92（新，🔴，第 2 次）“取地址物化”和“寄存器溢出”是两件事

- 现象：`&box` 那版 0.6390 ms（19.3%）。
- 准确说法：**寄存器没有地址**，取地址 → 编译器必须把这 16 字节的 `box` 物化进 **local memory**（物理在显存，走 L1/L2）；此后每次 `box.x` 都是一次 local load。
- 区分指标只有一个：`launch__registers_per_thread`
  ```
  取地址（物化）→ 该变量不再占寄存器 → 寄存器数【偏低】
  真溢出        → 寄存器数顶到上限（~255）【很高】
  ```
- 一句话：**“取地址 → 寄存器变少；溢出 → 寄存器变多”**（反直觉，所以好记）。
- **为什么会混**：两者都表现为“变慢 + 变量不在寄存器里”，但一个是**主动搬走**，一个是**装不下挤出去**。

### E-94 · 内部屏障不保护"上一次调用的读者"

- **日期**：2026-10-30
- **场景**：`block_reduce` 开头那个 `__syncthreads()` 的作用，我问「哪个切换最危险」，我答「为什么会威胁？都设置了屏障」。
- **错在哪**：函数内部的屏障只保证**本次调用内部**的顺序（写完 warp 部分和 → 再读 → 再广播）。它管不了**跨调用**：调用 k 返回后，每个线程才去读 `smem[0]`；如果某个线程跑得快，进到 k+1 次调用并执行到 `smem[warp_id] = v`（warp 0 就是 `smem[0]`），就把慢线程还没读到的值覆盖了。
- **正确做法**：函数**开头**加一个 `__syncthreads()`（所有人的"读"都发生在写之前），或在每次调用后补一个。
- **三个切换的风险**：1→2、2→3、3→4 都存在，程度相当；只要删掉开头那道屏障就是概率性错误，不是必然错误。
- **状态**：🟡

### K-07 · 合并归约的成本账（float2 两值一归约）

- **屏障**：每次归约 3 个（开头 / warp 写回后 / 广播后）→ 4 次 = **12 个**；改成 2 次 = **6 个**（少 6，不是少 4）。
  `屏障数 = 调用次数 × 3`
- **shuffle**：每次归约 = warp 内 5 次（offset 16→1）+ warp0 收 8 个值的 3 次 = **8 次**；4 次 = 32 次。
  两值一归约：每个 offset 做 2 次 shuffle → 16 次/调用 × 2 次 = **仍是 32 次**。
  `shuffle 数 = 值的个数 × 8`，与"几次归约"无关。
- **一句话**：合并归约省的是**屏障**（延迟），不是 shuffle（指令）。

### E-95 · `atomic_add` 是什么，为什么 dq 不用它、dk/dv 必须用（🔴 第一次出现就当题考）

- **日期**：2026-11-03
- **场景**：台阶 2 的 grid 是 `(S/BLOCK_M, B*H)`；我问「为什么 `dq` 直接 `store` 而 `dk/dv` 要 `atomic_add`」，答「不知道，不是还没学吗」。**这个反应是对的，是我出题失格。**
- **概念（补课）**：
  ```cuda
  atomicAdd(&dk[j*D+d], val);   // 语义：把 val 加到 *ptr 上，整条"读-改-写"不可被打断
  ```
  - 普通 `store` 是**覆盖**：谁最后写，谁说了算。
  - `atomic_add` 是**累加**：32 条 lane 同时往同一个地址加，硬件保证一次只让一个进去，一个都不丢。
  - 代价①：走 L2 的原子单元，吞吐远低于普通 store（争用越多越慢）。
  - 代价②：**浮点加法的顺序不定** → 每次运行结果差最后几位，**不可复现**。
- **为什么 dq 不用**：行（`pid_m`）是**并行切**的 → 第 i 行只由管它的那一个 program 产生 → 没有第二个 program 会碰 `dq[i]` → 直接 `store`。
- **为什么 dk/dv 必须用**：key 维**没并行**，是在 `for j` 里串行循环的 → 每个 program 都对**所有** key 行有一份贡献 → 16 个 program 同时往 `dk[j]` 加 → 必须 `atomic_add`。
- **一句话**：**一行数据只被一个 program 碰 → store；被多个 program 碰 → atomic。**
- **台阶 3 为什么改掉 atomic**：改成 `partial[SPLIT, ...]` 缓冲 + 归约 kernel，既去掉原子争用，又让结果可复现。
- **为什么第一次出现就当题考**：不该。已在 `docs/04-复习/` 的抽查协议里补一条：**新概念必须先讲过、用户复述过一次，才能出题。**
- **状态**：🔴（概念补完了，下次抽查要能复述"谁碰谁 atomic"）

### E-96 · TF32：`tl.dot` 默认不是真 fp32，判据要跟着输入精度定（🔴）

- **日期**：2026-11-03
- **场景**：台阶 2 每个 `tl.dot` 都写了 `input_precision="ieee"`，我问「不写会怎样、判据为什么是 1e-5」，答「不是跳过 tensor core 用 cuda core 吗」。
- **补课：fp32 矩阵乘在 GPU 上的三条路**
  | 路径 | 尾数位 | 相对误差 | 速度 |
  |---|---|---|---|
  | `ieee`（真 fp32，走 CUDA Core / 新卡的 fp32-TC） | 23 | ~1e-7 | 慢 |
  | **TF32**（tensor core 的"准 fp32"） | **10** | **~1e-3** | 快 ~8× |
  | fp16/bf16 输入 | 10 / 7 | 1e-3 / 1e-2 | 最快 |
- **关键事实**：Triton 的 `tl.dot` 遇到 **fp32 输入**，**默认走 TF32**（等于把 fp32 砍成 fp19）。
  → 于是 `1e-5` 的判据**永远过不了**，而且你会误判成"公式写错了"。
- **判据不是拍脑袋，是"输入精度 × 累加精度"的函数**：
  ```
  输入 fp32 + ieee        → 1e-5
  输入 fp32 + tf32        → 1e-2
  输入 fp16 + fp32 累加    → 2e-3
  输入 bf16 + fp32 累加    → 1e-2
  ```
- **什么时候可以不写 `ieee`**：输入本来就是 fp16/bf16 时——精度损失来自输入本身，与 `input_precision` 无关，此时用 Tensor Core 才是对的。
- **一句话**：**判据要跟"最低精度的那一环"对齐；fp32 走 TF32 就只剩 1e-3 的底噪。**
- **状态**：🔴

### E-97 · 共享内存账：`num_stages × (k 块 + v 块) + 中间缓冲`（🔴 算术题不会）

- **日期**：2026-11-03
- **场景**：台阶 2 第一次跑报 `OutOfResources: Required: 114688, Hardware limit: 101376`，我问「114688 里 k/v 流水线占多少」，答「不知道」。
- **算式（`BLOCK_M=BLOCK_N=64, D=64, fp32, num_stages=3`）**：
  ```
  k 块 = 64 × 64 × 4 B = 16 KB
  v 块 = 16 KB
  一级流水 = k + v = 32 KB
  num_stages=3 → 32 × 3 = 96 KB = 98304 B
  114688 − 98304 = 16384 B = 16 KB   ← 一块 (64,64) fp32 的中间缓冲（s / trans(k) 之类）
  ```
- **为什么 `num_stages` 吃的是共享内存**：软件流水（`cp.async`）要预先把下 n 级的数据搬进 shared，才能让计算与搬运重叠 → **级数 × 单级大小 = 预取缓冲总量**。寄存器里放不下这种东西。
- **三种降到 101376 以下的办法**：
  | 办法 | 结果 | 代价 |
  |---|---|---|
  | `num_stages=2` | 96 → 64 KB | 少一级预取，延迟隐藏变弱 |
  | `BLOCK_N=32` | k/v 块各 8 KB → 3 级 48 KB | 循环次数翻倍，每次搬运更碎 |
  | 切 fp16 | k/v 块各 8 KB → 3 级 48 KB | 精度降到 2e-3，但能用 Tensor Core |
- **一句话**：**共享内存 = 每级 tile 字节数 × 级数 + 中间结果缓冲；先算这个，再谈占用率。**
- **状态**：🔴（面试高频，必须能手算）

### E-98 · `delta` 的两种算法：分块版只能用 `do∘o` 那个（🟡）

- **日期**：2026-11-03
- **场景**：问「台阶 2 为什么必须先用 `_bwd_preprocess` 算 δ」，只答出公式、没答"手里有什么"。
- **两个等价公式**：
  $$\delta_i=\sum_d do_{id}\,o_{id}\quad(\text{需要 } o,do:\ S\times D)$$
  $$\delta_i=\sum_j dp_{ij}\,p_{ij}\quad(\text{需要整行 } dp,p:\ S\times S)$$
- **分块版为什么只能用前者**：手里只有一块 `(BLOCK_M, BLOCK_N)` 的 `dp/p`，**拿不到整行**；而 `o, do` 是 `S×D`，按行取永远取得全。
- **和 `lse` 的共同点**（这是本题的真正考点）：都是 **O(S) 的小数组**，都由**额外一个 pass 预算好**，再当主 kernel 的输入。
  - `lse`：前向存下；
  - `delta`：反向开头一个 preprocess kernel 算（`grid=(S//BLOCK_M, B*H)`）。
  - 目的都一样：**主循环里绝不物化 `S×S`**，这就是 FlashAttention 的"重算代替存储"。
- **一句话**：**能整行拿到、且是 O(S) 的量，就该单独一个 pass 算好当输入；拿不到整行的公式在分块版里直接淘汰。**
- **状态**：🟡
