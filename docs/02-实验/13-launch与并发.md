# 实验记录：launch 成本、多流与 CUDA Graph

> 记录时间：2026-10-27 晚 · 机器：RTX 4060 Laptop（AD107, 24 SM）+ WSL2 Ubuntu-22.04
> 代码：[`kernels/exp_sched.cu`](../../kernels/exp_sched.cu)（纯 C++/CUDA，不经 Python）
> 起因：`w8` 的 PagedAttention decode 已经到 **1.04 ms / 87.8% 实测带宽**，想知道剩下的时间是不是花在"启动"上。

---

## 0. 一句话结论

**在这台机器上，一次 kernel 提交要 8.5 µs，占 decode（1040 µs）的 0.8% → 单 kernel 不是 launch-bound。**
真正能省提交成本的是 CUDA Graph：重放一张图固定 3.6 µs、图内每节点 0.88 µs，**每层省 7.6 µs 且严格线性**。

---

## 1. 实验 A：一次提交多少钱

1000 次空 kernel 连发，`cudaEvent` 包住整批，重复 9 轮取最小。

| 提交方式 | 每次成本 |
|---|---|
| Python 循环 `mod.empty_launch()` | 8.2 µs |
| **纯 C++ 循环 `empty_kernel<<<1,32>>>()`** | **8.52 µs** |

两者几乎相同 ⇒ **pybind 不是瓶颈**。这 8.5 µs 是 WSL2 上每次 CUDA 调用穿虚拟化层的成本（原生 Linux 通常 1–2 µs，此条为引用、未在本机验证）。

**对 decode 的意义**：`8.5 / 1040 = 0.8%` ⇒ 优化单 kernel 时不用考虑启动开销。

---

## 2. 实验 B：多流能"流水线化提交"吗

4 条流各发 250 次空 kernel。

| 口径 | 单流 | 4 流 | 结论 |
|---|---|---|---|
| C++（取最小 9 轮） | 8.52 µs | **9.08 µs** | 更慢 6.7%（多 4 次 `cudaStreamSynchronize`） |
| Python（v2 脚本） | 10.58 µs | 8.35 µs | 快 21%，**不可复现** |

**结论：多流对"提交成本"没有收益。** Python 那次 21% 判定为噪声。
原因：这里的提交本身是同步阻塞的 syscall，CPU 没有"提前跑"的空间——所谓"提交流水线"在此环境不成立。

---

## 3. 实验 C：CUDA Graph 的收益是否随 N 线性

捕获 N 个空 kernel，测一次 `cudaGraphLaunch` 的时间。

| N | 整批 µs | 每节点 µs | 比单发省 µs |
|---|---|---|---|
| 1 | 8.2 | 8.19 | 0.33 |
| 2 | 5.1 | 2.56 | 5.96 |
| 4 | 7.2 | 1.79 | 6.73 |
| 8 | 10.0 | 1.24 | 7.27 |
| 16 | 15.4 | 0.96 | 7.56 |
| 32 | 29.7 | 0.93 | 7.59 |
| 64 | 61.4 | 0.96 | 7.56 |

最小二乘：**`整批 ≈ 3.6 µs（固定） + 0.88 µs × N`**

- 固定 3.6 µs ≈ **一次提交的价格**（`cudaGraphLaunch` 也是一次 syscall）
- 图内每节点 0.88 µs，与 N 无关
- `N=1` 整批 8.2 µs ≈ A 的 8.52 µs → **两套测量互相印证**

**收益公式**（`N` 为一步里的 kernel 数）：

```
省下 = 7.6 µs × N − 3.6 µs     拐点 N* ≈ 0.5 → N ≥ 1 就赚
```

graph 省的不是"语言开销"，是 **N−1 次提交**。

## 4. 实验 D：真正的并发（不是流水线）

4 个 `spin_kernel`，每个只占 1 个 SM（24 个 SM 里只用了 1 个）。

| 方式 | 时间 |
|---|---|
| 单个 spin kernel | 1549.3 µs（2,835,000 cycles） |
| 串行 4 次 | 4309.0 µs |
| **4 流并发** | **1135.6 µs** |
| 加速比 | **3.79×**（理想 4.00×，效率 **95%**） |

**顺带测出真实主频**：`2,835,000 cycles / 1549.3 µs = 1.83 GHz`，而 `prop.clockRate` 报 2.65 GHz（标称上限）。
⇒ 用 `clock64()` 换算时间必须反推实际频率，不能信标称值。

---

## 5. 两次证伪（本次实验最值钱的部分）

| 我的初始假设 | 实测结果 | 判定 |
|---|---|---|
| "8.2 µs 里约 6 µs 是 Python 绑定开销" | 纯 C++ 也是 8.52 µs | **证伪**：贵的是 GPU 调用路径，不是语言 |
| "多流能把提交流水线化，省 launch 成本" | C++ 里 4 流更慢 6.7% | **证伪**：提交是同步 syscall，无流水线空间 |

两次都是**换一种测量方式**才暴露的：换语言、换口径。这就是"交叉验证"的作用。

---

## 6. 怎么用（判据）

```
值得上 graph  ⇔  (7.6 µs × N − 3.6 µs) / 一步总时间  >  5%
```

| 场景 | 每步 kernel 数 | 省下 | 一步总时间 | 占比 | 值得？ |
|---|---|---|---|---|---|
| 我的单 kernel decode | 1 | 4.0 µs | 1040 µs | 0.4% | ❌ |
| 真实 32 层推理（每层 2–3 kernel） | 80 | 604 µs | 5000 µs | 12% | ✅ |

注意：`8.5 µs` 是 **WSL2** 的数字。原生 Linux 按 2 µs 估，同样 80 次提交只省 156 µs（3%）——**结论会翻转**。所以这个数必须带环境限定。
