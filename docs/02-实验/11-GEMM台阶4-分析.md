# GEMM 台阶4（Tensor Core）没达标：原因拆解与优化路线

日期：2026-10-24
当前状态：`gemm_tc` 跑通且结果正确（`cos≈1`），但只有 **0.85×**，未过 PyTorch fp32 基线。

## 一、差距有多大

| 项 | 时间 | TFLOPS | 占 fp16 峰值 65.2 |
|---|---|---|---|
| 台阶1 naive | 2.82 ms | 0.76 | 1.2% |
| 台阶2 shared tiling | 1.79 ms | 1.20 | 1.8% |
| 台阶3 寄存器分块 | 0.656 ms | 3.27 | 5.0% |
| **台阶4 Tensor Core（当前）** | **0.376 ms** | **11.4** | **17.5%** |
| PyTorch **fp32** matmul（基线） | 0.326 ms | — | — |
| 台阶4 的 mma 理论下限 | **0.033 ms** | 65.2 | 100% |

两个关键数字：

- **理论下限 33 µs**：全问题共 `1024³/16³ × 16 = 262144` 次 `m16n16k16` mma，每次 8192 FLOP，合计 2.147 GFLOP ÷ 65.2 TFLOPS = 33 µs。
- **实测 376 µs = 下限的 11.4 倍**。所以不是"mma 不够快"，是 **88% 的时间 warp 在等别的**。

带宽维度（16.7 GB/s = 峰值的 6.2%）说明：**内存完全不是瓶颈**，这是纯计算/调度问题。

## 二、没达标的五个原因（按影响排序）

### 1. 每个 warp 每轮只有 2 次 mma，然后立刻撞屏障（主因）

tile 的 K 宽 32 ÷ mma 的 K 宽 16 = 2 次 mma。mma 是**长延迟指令**（几十个周期才出结果），发射 2 条之后这个 warp 就没活了，只能等 `__syncthreads()`。

具体节奏（每轮 k0，32 轮）：

```
装载 8 个 half → 屏障 → load a → load b → mma → mma → 屏障 → 下一轮
```

warp 真正在算的时间占这一轮的比例很低，**mma 流水线大部分时间是空的**。

### 2. C tile 只有 32×32，装载摊得太薄

一个 32×32 的 C tile 需要 `As` 32×32 + `Bs` 32×32 = 2048 个 half。这 2048 个元素换来的是 4 warp × 2 = 8 次 mma。

换成 64×64 的 tile：`As` 64×32 + `Bs` 32×64 = 4096 个 half，换 16 warp × 2 = 32 次 mma。**同样一块共享内存的装载，服务的 mma 数翻 4 倍**。

### 3. 装载没有向量化：每指令只搬 2 字节

`As[r][c] = A[(bm*32+r)*K + k0 + c];` 是逐元素 half 赋值 → 编译成 `LDG.E.U16` + `STS.U16`，**一个指令 2 字节**。

一个 warp 的 32 个线程访问连续的 32 个 half = 64 字节，只用了半个 cache line 的带宽，而且**指令条数 ×8**。改成 `half2`（4 字节/指令）或 `uint4`（16 字节/指令）能把这个循环的指令数砍到 1/2 ~ 1/8。

### 4. 屏障次数多：每个 block 64 次

32 轮 × 2 次 = 64 次 `__syncthreads()`。4 个 warp 的 block 里，屏障的代价是"等最慢的那个 warp"，而 warp 之间进度不一（mma 延迟不同），实际等待时间远超屏障本身的开销。

### 5. block 太小，SM 上的 warp 并发不够填流水线

block 128 线程 = 4 warp，共享内存 8 KB。虽然 SM 能同时驻留多个 block，但**每个 block 内只有 4 个 warp 相互独立**，块内很难靠 warp 切换隐藏 mma 延迟。

## 三、优化路线（三步，按性价比）

| 步骤 | 做什么 | 预期收益 | 今天做？ |
|---|---|---|---|
| **① 放大 tile 到 64×64** | 16 warp、每 warp 4 个 16×16 子块或 1 个子块 + 更大 K 摊薄 | 0.376 → **0.12–0.18 ms** | ✅ 做 |
| ② 向量化装载 | `half2`/`uint4` 搬 As/Bs | 再降 10–25% | 明天 |
| ③ 双缓冲（`cp.async`） | 装载与计算重叠，屏障从 64 次降到 32 次 | 再降 15–30% | 之后 |

**今天只做 ①。** ②③ 会改装载代码的结构，等 ① 的收益确认了再上，否则两个变量混在一起无法归因。

## 四、第一步：64×64 tile 的具体做法

### 4.1 新的形状

| 项 | 台阶4（现在） | gemm_tc2 |
|---|---|---|
| C tile | 32×32 | **64×64** |
| block | `(32,4)`=128 线程，4 warp | `(32,8)`=256 线程，**8 warp**；或 `(32,16)`=512 线程，16 warp |
| grid | `(N/32, M/32)` = 1024 块 | `(N/64, M/64)` = **256 块** |
| 每 warp 负责 | 一个 16×16 | 一个 16×16，warp 排 4×4（16 warp 版）或 2×4（8 warp 版） |
| `As` | `[32][32]` 2 KB | `[64][32]` **4 KB** |
| `Bs` | `[32][32]` 2 KB | `[32][64]` **4 KB** |
| `Cf` | `[32][32]` float 4 KB | `[64][64]` float **16 KB**（或直接转 half 缓冲 8 KB） |
| 共享内存合计 | 8 KB | 24 KB（用 half 缓冲则 16 KB）|

> 建议先用 **8 warp / 每 warp 2 个 16×16 子块**（warp 排 2×4），共享内存压力小、改动最少；跑通后再考虑 16 warp。

### 4.2 装载怎么改

线程数 256，要搬 `64×32 + 32×64 = 4096` 个元素 → **每线程 16 个**。用 `half2` 搬就是 8 次：

```cpp
int btid = ty * 32 + tx;                 // 0..255
// A 块：64 行 × 32 列（K 方向）
for (int i = btid; i < 2048; i += 256) {
    int r = i / 32, c = i % 32;
    As[r][c] = A[(bm * 64 + r) * K + k0 + c];
}
// B 块：32 行（K）× 64 列（N）
for (int i = btid; i < 2048; i += 256) {
    int r = i / 64, c = i % 64;
    Bs[r][c] = B[(k0 + r) * N + bn * 64 + c];
}
```

### 4.3 mma 怎么改

```cpp
int warp = ty;                 // 0..7
int warp_m = warp / 4;         // 0..1
int warp_n = warp % 4;         // 0..3
// 一个 warp 管 C 的两块 16×16：行方向 stride 32（因为 M 方向只有 2 层）
```

单块（每 warp 只算一个 16×16，需要 16 warp 版）最省事：`warp_m = warp/4`、`warp_n = warp%4`。

内层仍然要按 mma 的 K=16 切：

```cpp
for (int kk = 0; kk < 32; kk += 16) {
    load_matrix_sync(a, &As[warp_m*16][kk], 32);     // ldm 仍是 32（As 的行宽）
    load_matrix_sync(b, &Bs[kk][warp_n*16], 64);     // ldm 变成 64（Bs 的行宽是 64）
    mma_sync(c, a, b, c);
}
```

**注意 `ldm` 变了**：`As` 是 `[64][32]` → 行宽 32；`Bs` 是 `[32][64]` → 行宽 **64**。这是这次改动里最容易错的一处。

### 4.4 写回

```cpp
store_matrix_sync(&Cf[warp_m*16][warp_n*16], c, 64, wmma::mem_row_major);  // ldm = 64
__syncthreads();
for (int i = btid; i < 4096; i += 256) {           // 64×64 = 4096
    int r = i / 64, c = i % 64;
    C[(bm*64 + r)*N + bn*64 + c] = __float2half(Cf[r][c]);
}
```

### 4.5 验收

```bash
~/miniconda3/envs/triton/bin/python kernels/bench_kernels.py --only gemm
```

| 结果 | 判断 |
|---|---|
| `> 0.3 ms` | 没赚到，检查 `ldm`（32/64）和 `warp_m/warp_n` 映射 |
| `0.15–0.25 ms` | 正常，比台阶4 快 1.5–2.5× |
| `< 0.13 ms` | 超出预期，直接进 ② 向量化 |

目标：**TFLOPS > 20、加速 > 1.0×**（越过 PyTorch fp32 基线）。

## 五、为什么要现在做这一步

台阶4 的价值不是"跑通 wmma"（那个 4a 预演已经证明了），而是**证明你知道 Tensor Core 的正确用法**。当前 0.85× 在简历上是"用了张量核心但仍然比 PyTorch 慢"，很难讲；到 25 TFLOPS 就是"手写 Tensor Core GEMM，比 PyTorch fp32 快 2 倍"，可以直接写进项目。

另外，这一步学到的三件事——**tile 尺寸决定摊薄、mma 的 K 必须整除 tile 的 K、ldm 跟着 tile 宽度变**——是后面所有 Tensor Core 算子（attention 的 QK^T、PV）共用的。
