# GEMM 从 24× 到「同进程 cuBLAS 的 98%」

> 口径：**M = N = K = 1024，fp16 输入、fp32 累加、fp16 输出**，基线是同进程 `torch.matmul`（cuBLAS）。
> 日期：2026-11-17。文件：`kernels/w6_2gemm.cu`（旧，wmma）→ `kernels/w6_3gemm.cu`（新，mma.sync）。

## 一句话结论

把 tile 从 **128×128 改回 64×64**，性能从 cuBLAS 的 83% 跳到 **最高 98%**。
不是因为复用率（大 tile 复用率高），而是因为**尾波**：1024³ 上 A+B 只有 4 MB、L2 有 24 MB，
流量根本不是瓶颈，而 128×128 的 grid 只有 64 块、2 block/SM 只能并发 48 块 → 1.33 波 → 效率 67%。

## 0. 先说测量：不比同一次运行里的 cuBLAS，数字没有意义

| 现象 | 数据 |
|---|---|
| 同一份 cuBLAS 在不同轮里 | **0.1141 / 0.1143 / 0.1215 / 0.1339 / 0.1451 / 0.1504 ms**（差 32%） |
| 我们同一份 kernel | 0.1167 / 0.1168 / 0.1391 / 0.1464 ms（差 25%） |

4060 Laptop 有功耗墙，**谁后跑谁吃高时钟**。第一版 driver 每轮固定「先 ours 后 cuBLAS」，
cuBLAS 永远后跑 → 比值被系统性压低了约 20%。**现在奇数轮交换先后顺序**，并且：
丢第 1 轮（cuBLAS 首次有 2–4 ms 的选核开销）、6 轮取中位数。

## 1. 四个配置的对照（这是本次最值钱的部分）

| 配置 | 线程 / warp 排布 | 累加器 | 寄存器 | block/SM | grid | 波数 | 效率 | 结果 |
|---|---|---|---|---|---|---|---|---|
| BM=256, BN=128 | 512 / 4×4 | 64 | 125 | 1 | 32 | 32/24=1.33 | 差 | **0.2405 ms（58%）** |
| BM=128, BN=128 | 256 / 2×4 | 64 | 125 | 2 | 64 | 64/48=1.33 | 67% | 0.1391 ms（83%） |
| BM=128, BN=64 | 256 / 2×4 | 32 | 94 | 2 | 128 | 128/48=2.67 | 74% | 0.2085 ms（70%） |
| **BM=64, BN=64** | **128 / 2×2** | **32** | **92** | **5** | **256** | **256/120=2.13** | **89%** | **0.1168 ms（98%）** |

三条结论：

1. **block 越少越吃亏**。256×128 只有 32 块、每 SM 1 块 → 24 块并发跑 32 块，第二轮只有 8 块在跑 → 58%。
2. **加 warp 不一定好**。128×128 用 8 warp（512 线程）→ 寄存器 125 撞到 65536 上限，每 SM 只放得下 2 块，占用率 33%。
3. **小 tile + 多 block 能同时改善占用率和尾波**。64×64 用 4 warp（128 线程）、累加器 32 个 → 92 regs →
   每 SM **5 块 = 20 warp = 42% 占用**，而 block 数 256 让尾波只剩 11% 损耗。

## 2. 反例也要记下来：三次白费的尝试

| 尝试 | 预期 | 实测 | 为什么失败 |
|---|---|---|---|

| STAGES=3 三级流水 | 加载更早藏起来 | 0.1764 ms（82%） | smem 48 KB 仍只 2 block；`% 3` 环形索引不是 2 的幂，多了一堆整数运算 |
| BK=32 → 64（想减半屏障） | 屏障 64 次 → 32 次 | 未采用 | smem 64 KB → 1 block/SM，8 warp = 17% 占用，得不偿失 |

## 3. 98% 那版怎么实现的（`kernels/w6_3gemm.cu`，218 行）

### 3.1 线程与片段划分

- block 64×64，**4 个 warp**（128 线程），排成 2(M)×2(N)；每个 warp 算 **32×32**
- 每个 warp：m 方向 2 个 16、n 方向 4 个 8 → `acc[2][4][4] = 32` 个 float
- 片段语义（全部自己摆，不依赖 wmma）：
  - A（m16k16，4 个寄存器）：`ldmatrix.x4`，lane 地址 `As + swz_a(m0 + lane%16, k0/8 + lane/16)`
  - B（k16n8，2 个寄存器）：Bs 按 `[k][n]` 存（cp.async 只能顺着 N 拷），用 `ldmatrix.x2.**trans**` 转置取
  - C（m16n8，4 个 float）：`c0,c1 = C[m0 + lane/4][n0 + (lane%4)*2 + 0,1]`，`c2,c3` 是行 +8

### 3.2 三个关键实现点

1. **`mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32`**
   一条指令吃掉 16×8×16 的乘加（= 8192 条 FFMA 的工作量），A/B 走 `.f16` 寄存器、累加器留 `.f32`。
2. **XOR swizzle 代替 padding**
   `swz_a(m, g) = m*BK + ((g ^ (m & 3)) << 3)`、`swz_b(k, g) = k*BN + ((g ^ (k & 7)) << 3)`
   —— 8 个 half（16 B）当一组，组号与行号异或，把同一列的访问摊到不同 bank；写和读用**同一个函数**，
   所以 cp.async 的写地址和 ldmatrix 的读地址自动对上。
3. **cp.async 双缓冲**
   `cp.async.cg.shared.global [dst], [src], 16` 直接全局→共享、不过寄存器；
   每 stage 一次 `commit_group`，进循环时 `wait_group 1`（放掉一个 → 当前 stage 就绪），
   计算与下一 stage 的搬运重叠。

### 3.3 epilogue

`__floats2half2_rn` 把 `(c0,c1)`、`(c2,c3)` 各打成一个 32 位字存回（4 B 对齐），
比起逐元素 `C[i] = half(x)` 省一半指令。128 位存（`uint4`）还没做——它需要 smem 中转转置，
在 K 循环 32 次、epilogue 只 1 次的比例下收益很小。

### 3.4 SASS 与资源

```
16 HMMA.16816.F32          每条 = 16×8×16 MAC
24 LDGSTS.E.BYPASS.128     cp.async 16 B（128 位）搬运
4  LDSM.16.M88.4           ldmatrix.x4（A）
8  LDSM.16.MT88.2          ldmatrix.x2.trans（B，MT = 转置）
92 registers, 0 spill      16 KB smem/block → 5 block/SM，42% 占用
```

## 4. 怎么复现

```bash
# WSL，需先把 ninja 和 nvcc 加进 PATH
export PATH=$HOME/miniconda3/envs/triton/bin:/usr/local/cuda/bin:$PATH
cd ~/projects/aigpu-lab && python kernels/w6_3gemm.py
```

driver 会先对 `A.float() @ B.float()` 做正确性检查（当前相对误差 **3.9e-4**），
再交替测 6 轮（奇数轮交换顺序）、丢第 1 轮、取中位数。

## 5. 面试口径（三句）

1. 「1024³ 上我做到同进程 cuBLAS 的**最高 98%**（0.1168 ms / 18.4 TFLOPS），不是每个观测状态都 98%——
   cuBLAS 自己在不同轮里漂 32%，所以我只报同一次运行内的比值。」
2. 「关键不是用上 Tensor Core，而是**尾波**：128×128 的 grid 只有 64 块、每 SM 2 块 → 1.33 波、效率 67%；
   换 64×64 + 4 warp，累加器 64→32、寄存器 125→92、每 SM 5 块，256 块把尾波摊到 89%。」
3. 「三个反例我都留着：256×128 掉到 58%、128×64 掉到 70%、强压 3 block/SM 触发 spill 掉到 63%。
   这些都是我一开始算错了『流量=带宽瓶颈』——A+B 只有 4 MB，L2 24 MB 全命中，流量根本不重要。」
