# FlashAttention 反向：五个台阶

> 目标：不是"跑通一个 attention 反向"，而是**每一步只引入一个新变量**，让报错可归因。
> 代码：`kernels/w11_attn_bwd.py`（台阶 1–4）+ `kernels/w11_oracle.py`（台阶 0 的尺子）
> 配置：`B=1, H=8, S=1024, D=64`，卡 RTX 4060 Laptop（fp16 峰值 65.2 TFLOPS，实测带宽 221.4 GB/s）

## 一、五个台阶

| 台阶 | 做什么 | 判据 | 结果 |
|---|---|---|---|
| 0 | PyTorch 手写 8 行梯度公式，与 autograd 对账 | `1e-5` | **6.1e-16** ✅ |
| 1 | Triton 单块（S=64，一个 program 一个 `(b,h)`） | `1e-5` | dq 3.6e-7 / dk 3.6e-7 / dv 1.8e-7 ✅ |
| 2 | 分块 + `atomic_add`（S=1024，`grid=(16,8)`） | `1e-5` | dq 6.0e-7 / dk 5.4e-7 / dv 4.8e-7 ✅（5.03 ms） |
| 3 | 拆两 kernel，`dk/dv` 与 `dq` 各自独占一维 → **无 atomic** | `1e-5` + 逐位可复现 | 5.50 ms，1.09× 台阶2 ✅ |
| 4 | fp16 + Tensor Core | `2e-3` | **0.514 ms**，误差 3.9e-4，**10.8×** ✅ |

**为什么台阶 0 不能省**：台阶 1 报 `max_abs=3e-2` 时，必须先能排除"公式错"，否则会去改根本没错的代码。

## 二、性能

| 实现 | 时间 | 相对前向 | 相对台阶2 | 有效算力 |
|---|---|---|---|---|
| 前向（PyTorch 手写 fp32，物化 S²） | 2.216 ms | 1.00 | — | — |
| 台阶 2（fp32 + ieee + atomic） | 5.026 ms | 2.27 | 1.00 | 0.73 TFLOPS |
| 台阶 3（fp32 + ieee，无 atomic） | 5.502 ms | 2.48 | **1.09** | 0.73 TFLOPS |
| **台阶 4（fp16 + TC）** | **0.514 ms** | 0.23 | 0.10 | 6.19 TFLOPS（口径见下） |
| *参考*：PyTorch SDPA 前向 | 0.435 ms | — | — | — |
| *参考*：PyTorch SDPA **反向**（autograd） | **0.309 ms** | — | — | — |

三个结论：

1. **去掉 atomic 只贵 9%**，不是原先估的 +50%。原因：多算一遍 `p/ds` 的代价 ≈ atomic 争用的代价，两者互相抵消。**这是本实验最有价值的一个反直觉数据。**
2. **fp16 提速 10.85×**，远超"精度减半"能解释的范围——真正的收益是**打开了 Tensor Core**（`ieee` 让 `tl.dot` 全程走 CUDA Core）。
3. 台阶 4 的 0.514 ms 比"前向 2.216 ms"还快 4.3×。这不是反常，而是因为**前向是 PyTorch 手写的 fp32 版本**（物化了 `S×S` 并调用 `softmax`），不是 SDPA。**两个数不是一个口径，报告时必须写清。**

### 唯一可对外的对比：PyTorch SDPA 反向

`F.scaled_dot_product_attention` + `torch.autograd.grad` 的反向，同形状同 dtype（`B=1,H=8,S=1024,D=64`，fp16），3 轮取最小 = **0.309 ms**。自写版 **0.514 ms = 1.66×**。

三个口径差异（写报告时一并交代，否则会被追问）：
1. 自写版多一个 `_bwd_preprocess` kernel（预算 `delta`，一趟读写 `o/do` 共 1 MB），cuDNN 的 flash 反向在核内算；
2. 自写版 `BLOCK_M/BLOCK_N = 64`、无 cp.async 流水，cuDNN 用 128×128 tile + 多级流水；
3. 两者都不是因果掩码、都把 `lse/delta` 存 fp32 —— 这一点一致。

**结论口径**："从零写的 Triton 反向是 PyTorch 内置 flash 反向的 1.66×（同形状同精度），差距定位在缺流水与预处理独立成 kernel"，不要说"接近"或"超过"。

### 算力口径

打印用的 `flops = 6·B·H·S²·D = 3.2 GFLOP`，但台阶 3/4 实际执行了 **7 个** `S²·D` 的 matmul（两个 kernel 各自算一遍 `q·kᵀ` 和 `do·vᵀ`，加上 `dkdv` 里的 `dsᵀq`、`pᵀdo` 和 `dq` 里的 `ds·k`）：

```
真实 ≈ 7·B·H·S²·D = 7.5 GFLOP
→ 0.520 ms 下 ≈ 14.4 TFLOPS ≈ 峰值的 22%
```

剩下 78% 的损失来自两处：`ds`/`p` 的累加 dot 还在 fp32（走 CUDA Core）、以及 64×64 的小 tile 撑不满。

## 三、四个关键决策

### 1. 为什么 `tl.dot` 必须写 `input_precision="ieee"`

Triton 对 **fp32 输入**默认走 **TF32**（尾数 23→10 位），误差底噪 ~1e-3。`1e-5` 的判据永远过不了，而且看起来像"公式全错"。台阶 3 的骨架我漏写过一行，结果三处误差全是 1e-3 量级 —— 现成的教材。

### 2. 为什么 `dq` 不用 atomic，`dk/dv` 必须用

- **行（query）被并行切**：第 i 行只由一个 program 产生 → 直接 `store`；
- **key 维没并行**（在 `for j` 里串行）：所有 program 都对每个 key 行有贡献 → 必须 `atomic_add`；
- 代价：atomic 走 L2 原子单元，且**浮点加法顺序不定 → 不可复现**。

### 3. 台阶 3 为什么不"再往 grid 里加一维"，而是拆成两个 kernel

加一维的话，`dk/dv` 仍被多个 program 碰，冲突只变少不消失，最后还得 `partial + 归约`。拆成两个 kernel 让**每个 program 独占自己那一块**，循环里累加进寄存器，结束时一次 `store`：

| kernel | grid | 串行循环 | 独占输出 |
|---|---|---|---|
| `_bwd_dkdv` | `(S/BLOCK_N, B*H)` | 走 query 块 | `dk`, `dv` |
| `_bwd_dq` | `(S/BLOCK_M, B*H)` | 走 key 块 | `dq` |

代价：`p`、`ds` 各算两遍（+real FLOPs），换来**没有原子争用 + 逐位可复现**。

### 4. `num_stages` 与共享内存

默认 `num_stages=3`。台阶 2/3 直接 `OutOfResources: 114688 > 101376`：

```
k 块 16 KB + v 块 16 KB = 32 KB/级 × 3 = 96 KB + 中间缓冲 16 KB = 114688 B
```

降到 2 级 → 64 + 16 = 80 KB，通过。**共享内存 ≈ 级数 × 每级 tile 字节 + 中间缓冲**。

## 四、误差

| 台阶 | 误差 | 来源 |
|---|---|---|
| 0 | 6.1e-16 | 双精度对拍 |
| 1–3 | ~5e-7 | fp32 + ieee 的累加顺序差（1e-5 判据的 1/20） |
| 4 | 3.9e-4 | **fp16 输入本身的舍入**（相对 5e-4），被 `√D=8` 摊薄一次 |

## 五、可复现性

台阶 2 连跑两次结果不同（atomic 顺序不定）；台阶 3 用 `torch.equal` 比对两次结果 **完全一致**。这是"无 atomic"唯一能用一行代码验证的收益，也是面试里最好讲的取舍。

## 六、教训（已进错题本）

- **E-95**：`atomic_add` 是什么、谁碰谁 atomic；
- **E-96**：TF32 默认 + 判据怎么定（`fp32+ieee→1e-5`、`fp16→2e-3`）；
- **E-97**：共享内存账 = `num_stages × 每级 tile + 中间缓冲`；
- **E-98**：`delta` 两种算法，分块版只能用 `do∘o`（拿不到整行 `dp/p`），与 `lse` 同为"额外一个 pass 预算好的 O(S) 小数组"。
