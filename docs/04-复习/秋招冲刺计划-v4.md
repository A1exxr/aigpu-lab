# 15. GEMM 深度优化冲刺（用户 2026-10-29 决定要做，10/31–11/2）

## 现状（起点，别忘）

| 台阶 | 做法 | 时间 | TFLOPS | 相对 fp16 峰值 |
|---|---|---|---|---|
| 1 naive | 每线程 1 个 C 元素，直读全局 | 2.42 ms | 0.09 | 0.1% |
| 2 tiled | 32×32 共享内存 tile | 1.7840 ms | 1.20 | 1.8% |
| 3 寄存器分块 | block 8×8，每线程 4×4 | 0.6574 ms | 3.27 | 5.0% |
| 4 Tensor Core | `wmma` 16×16×16，C tile 32×32，单缓冲 | **0.2836 ms** | **7.57** | **11.6%** |
| 4b（反例） | C tile 放大到 64×64 | 0.3830 ms | 5.61 | 8.6% |

4b 的教训（这是本冲刺的全部动机）：
> 64×64 tile 让共享内存从 4 KB 涨到 24 KB，每 SM 驻留 block 数从 12 掉到 3，屏障期间没有别的 block 填计算空档 → 反而慢 35%。
> **所以“更大的 tile”不能单独上，必须和 double buffering（掩盖装载延迟）一起上。**

## 技术路线（按顺序，别跳）

1. **bank conflict 先修**：现在 `As[32][32]` 行距 32 个 half = 64 B，warp 读同一列时 4-way conflict。
   最小改法：`As[32][33]`（行距 66 B）——**但注意**：wmma 的 `load_matrix_sync` 要求 `ldm = 32`，加 padding 后 ldm 变 33，wmma 不支持 → **padding 只对“手写 FMA 读法”有效**。
   所以在 wmma 路线上，消 conflict 要靠 **swizzle**：`As[r][c ^ ((r & 7) * 4)]` 之类的 XOR 置换，读时再异或回去。
2. **每 warp 2×2 tile**：4 个 warp 各管 C 的 32×32 子块（64×64 总量），每 warp 用 2×2 个 `16×16×16` fragment。
   显存流量不变，但每 warp 的寄存器压力从 1 个 acc（8 个 float/线程）升到 4 个（32 个 float/线程）→ 要先算 `registers_per_thread`，别超过 128。
3. **double buffering**：两个 buffer 交替，`cp.async` 在算第 i 块时预取第 i+1 块，屏障从“每块 2 次”降到“每块 1 次”（`cp.async.wait_group`）。
   **4060 是 SM 8.9（Ada），支持 `cp.async`（Ampere 起就有），也支持 `cp.async.bulk`（Hopper 的 TMA 在 Ada 上没有完整支持，别碰）。**
4. **别碰的**：wgmma/tcgen05（需要 Hopper/Blackwell）、TMA descriptor、CUTLASS 集成（那是另一条线）。

## 已知风险

- **寄存器超限**：2×2 fragment + double buffer 的地址计算容易把寄存器顶到 168+ → 占用率塌方，比现在还慢。先用 `-Xptxas -v` 看 `registers`。
- **共享内存超限**：2 stage × 64×64 × 2 B = 16 KB × 2 = 32 KB，加 `Cf` 若留在共享内存就不够 → `Cf` 已经在寄存器（cumulator fragment），没问题。
