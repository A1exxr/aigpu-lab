# 面试 15 问（算子 / AI Infra 岗）

> 用途：一面 80% 的时间在问「讲一个你做的项目 + 难点 + 怎么定位」。这 15 问覆盖 8 个项目，每题给 **3 句话答案**（能一口气说完的长度）+ **1 条追问预警**。
> 原则：**答案里必须有一个数字、一个判断、一个"为什么"**。没有数字的回答等于没做。
> 数字口径：以仓库 `README.md` 为准（同一次全量测量）；面试前重测一遍，若偏低就说区间（如「8～8.5 倍」）。

## A. 通用 3 问

### A1. 介绍一下你自己

> 我是扬州大学管理科学与工程 2027 届硕士，方向是 GPU 算子优化。半年里我在 RTX 4060 Laptop 上从零手写了 10 个 CUDA/Triton 算子：访存型（reduce/softmax/gelu）、融合（RMSNorm+残差）、attention 全链路（naive → FlashAttention → PagedAttention → INT8）、GEMM 四台阶（到 Tensor Core）、以及 softmax/LayerNorm 反向。所有结论都有可复现的 bench 和 ncu 数据，代码在 github.com/A1exxr/aigpu-lab。

**追问预警**：为什么非科班做这个？→ 答"管理科学里的运筹优化本来就在算力边界上，我做过 CP-SAT/QUBO 的大规模求解，发现瓶颈在 GPU 侧，就往下走了"。

### A2. 你项目里最难的一个 bug

> `GELU` 我写了个 `float4` 向量化版本，结果比朴素版慢 3.3 倍（0.6390 vs 0.1956 ms）。查 ncu 发现 `registers_per_thread` 只有 20 出头、local memory 访问 18 次/线程——原因是 `reinterpret_cast<half*>(&box)` 取了局部变量地址，寄存器没有地址，编译器被迫把 16 字节物化到 local memory（物理在显存）。改用 `__half2` 全程零 `&`（`__half22float2` 是值→值转换），同一份数据做到 0.1516 ms、81.4% 带宽，追平 PyTorch。

**追问预警**：怎么区分"取地址物化"和"寄存器溢出"？→ 看 `registers_per_thread` 的方向：物化偏低、溢出很高。

### A3. 你怎么判断一个 kernel 该不该继续优化

> 三步：先算字节账（读多少、写多少 → 理论下限 ms），再看 ncu 的 `dram__throughput` 到没到 85%，最后看 `warps_active` 确认并行度没拖后腿。三个数一起读才能定性：`DRAM 高 + warp 高 + SM 低` 是访存受限的正常签名，该停手；`DRAM 低 + warp 低` 才是并行度不够，去调 block/寄存器。

**追问预警**：如果 DRAM 到 92% 但你还要更快？→ 只能减字节（融合、量化、改问题），不能再"优化"。

## B. 8 个项目 · 10 问

### B1. Reduce（w2_reduce：0.1137 ms，ncu DRAM 87.3%）

> 两级归约：warp 内用 `__shfl_down_sync` 五轮（16→1，零屏障），跨 warp 才走共享内存（写 + 1 屏障 + warp0 再 shuffle）。ncu 显示 `dram__throughput 87.25%`、`warps_active 94.88%`、`sm__throughput 39%`——标准的访存受限，已经贴墙，所以我停在这里，没再花时间。

**追问预警**：为什么不全部用共享内存做归约？→ 每级都要屏障，屏障成本 0.8–2.6 µs/次，warp 内用 shuffle 是零成本。

### B2. Softmax（屏障 20 → 4，0.2160 ms）

> 第一版按教科书写两级归约，一行 softmax 要 3 次逐行归约、共 20 个屏障。我把级别 1（warp 内）全换成 shuffle，只保留跨 warp 的「写 → 屏障 → 广播」两段，降到 4 个屏障，0.2478 → 0.2160 ms。再往下减收益就没了：剩下 4 个屏障约 3.5 µs，只占 216 µs 的 1.6%，而且 ncu 已显示 `sm__throughput 87.96%`，瓶颈转到 SM 吞吐，属于 Amdahl 意义上的白干。

**追问预警**：屏障单价怎么测出来的？→ 两轮对比：20→10 省 26.6 µs（单价 2.66 µs），10→4 省 5.2 µs（单价 0.87 µs）——后一轮减的屏障能被其他 warp 掩盖，所以更便宜。

### B3. GELU（0.1956 → 0.1516 ms，81.4%）

> 三个版本：朴素（0.1956 ms / 63.1%）、`float4` 取地址坏版（0.6390 / 19.3%）、`__half2` 好版（0.1516 / 81.4%）。关键认识是"向量化省的是指令条数不是字节数"：`half` 每指令 2 B、`__half2` 每指令 4 B，指令数减半，同时在飞的请求数翻倍，才把带宽从 63% 推到 81%。

**追问预警**：为什么不用 `float4`？→ `float4` 是给 fp32 准备的 16 B 箱子，数据是 fp16 时用它就得 `reinterpret_cast` 加取地址，正好踩物化的坑。

### B4. RMSNorm + 残差融合（5N → 3N，0.1999 ms，92.8%）

> 分步实现是 5 流 80 MB（读 x、读 res、写 h、读 h、写 out），融合后是 3 流 48 MB——中间结果 h 只存在于寄存器，不落显存，理论加速上限 1.25×（不是想当然的 2×，因为 5N/3N 有下限）。实测 92.8% DRAM 带宽、比两个 kernel 的实现快 1.95×。它教我的事：**融合的收益上限由字节数决定，算清楚再动手**。

**追问预警**：为什么不是 5/3 = 1.67×？→ 5N 里有两份是"写 h + 读 h"，融合省掉的是这 2N，剩下 3N 里读 x、读 res、写 out 一份都省不掉。

### B5. Attention naive → warp-per-j（46.9 → 15.5 ms）

> 第一版 QK 阶段每个线程读一整行 K，warp 内 32 个线程的地址间隔 128 B，一条 32 B 的 sector 只用 2 B，扇区利用率 6.25%。改成 warp-per-j（warp 管一个 j，lane 切 d 维）后利用率 100%，qk 从 34.3 ms 掉到 14.8 ms。剩下的是 PV 阶段只有 64/256 线程在干活，四路切 j 后到 15.5 ms 总时间——3 倍加速，但离 1.05 ms 的带宽下限还差 15 倍，因为 naive 写 S² 矩阵本身就是错的算法。

**追问预警**：为什么扇区利用率是 6.25% 而不是 1.56%？→ cache line 128 B 里用 2 B 是 1.56%，但 GPU 按 32 B sector 计费，2/32 = 6.25%；DRAM 按 sector 算，所以对外说 6.25%。

### B6. FlashAttention（Triton，0.474 ms，SDPA 的 91%）

> 核心是 online softmax：不物化 S×S 矩阵，而是按块累加 `m`（行最大值）、`l`（分母）、`acc`（分子），每来一块新的 K/V 就用 `alpha = exp(m_old − m_new)` 同时缩放分子和分母。实测 0.474 ms，是 PyTorch SDPA 的 91%，相对自己写的 naive 版快 32.8×。它让我第一次看清"算力受限"长什么样：流量只有 4·S·d = 16 MiB，带宽利用率 12.5%，但算力到 27.8% × 65.2 TFLOPS。

**追问预警**：`alpha` 为什么要同时乘分子和分母？→ 分子分母都是"以 m 为基准的 exp 之和"，基准换了必须同比缩放，否则比值错。

### B7. GEMM 四台阶（2.42 → 0.2836 ms，8.5×，1.13× vs PyTorch fp32）

> naive（每线程 1 个 C，直读全局）2.42 ms → 共享内存 tiling 1.78 → 4×4 寄存器分块 0.66 → `wmma` Tensor Core 0.2836 ms，相对 PyTorch fp32 matmul 是 1.13×。关键账：tiled 版每个 C 元素要 2048 次 smem 读，寄存器分块把"每次读服务的 FMA 数"从 0.5 提到 2，smem 读总量降到 1/4；Tensor Core 则直接绕开手写读取模式，把数据成块搬进寄存器。

**追问预警**：为什么 NN/NT/TN 三种布局都写了？→ **不是比快慢，是三种用法各自的形状**：前向 `Y = X·W` 是 NN，反向 `dA = dY·Bᵀ` 是 NT，反向算 `dW = dYᵀ·X` 时 A 天然存成 `[K,M]`，就是 TN。布局由数据从哪来决定，不由我挑；我要做的是让三种都能算对，并且知道 TN 装载 tile 时要按列取。

### B8. PagedAttention（fp16 1.2483 ms / 97.6% 实测带宽）

> 从两遍（2.3644）→ 单遍 online（1.8897）→ 2 路展开（1.5084）→ split-L 四段归约（1.2483），累计 1.89×。最后一步到 216 GB/s，是这台机器实测天花板 221.4 的 97.6%——也就是说这个 kernel 除了 merge 的 1 MiB，没有可省的流量了。相对 PyTorch 的参考实现是 6.70×，但要注意那个 ref 是逐 token 跑 2048 次 PagedAttention 的写法，不是 SDPA，**不能和 SDPA 比**。

**追问预警**：split-L 的代价是什么？→ 多一次写 + 一次读（partial 缓冲 1 MiB），占总流量 0.4%，换来 4 倍并行度。

### B9. INT8 量化（1.0419 ms / 87.8%；三个反例）

> 只量化 K：流量 256 → 193 MiB，1.5084 → 1.0419 ms，87.8% 带宽，这是正例。但接着把 V 也量化（130 MiB）反而慢到 1.2032 ms / 51.2%：因为每 lane 每指令只搬 1 B，warp 一条访存指令只带 32 B，在飞字节不够，发射能力成了新瓶颈。再加 `int8×4`（每指令 4 B）又碰上 warp 数不足，1.5503 ms。**这组反例的价值大于正例**：它证明"省字节 ≠ 变快"。

**追问预警**：那 INT8 到底什么时候有收益？→ 当"每指令字节数"能补回来（打包成 int8×4 + 足够的 warp）时；或带宽是唯一瓶颈、启动开销可忽略时。

### B10. 两个反向 kernel（softmax 0.2601 ms / 87.4%；LayerNorm 0.2980 ms / 81.8%）

> softmax 反向是 3N 流量、1 次归约，87.4% 带宽；LayerNorm 反向也是 6N... 准确说 6N（读 x、读 dy、写 dx），但要 4 次归约（mean、var、dot、sum），所以只有 81.8%。差别不在字节，在**归约次数**——4 次归约 = 12 个屏障，而且 `x̂` 要现场重建。优化方向写进文档了：用 `float2` 一趟带回两个值，屏障 12 → 6。

**追问预警**：LayerNorm 反向公式里三项各依赖什么？→ `dx = rstd·(dy − mean(dy) − x̂·mean(dy·x̂))`，其中 `mean(dy)` 和 `mean(dy·x̂)` 都是整行的和，必须先把 `x̂` 算出来（数据依赖 → 至少 2 趟）。

### B11. 调度层（launch 8.5 µs、Graph、多流）

> 我量了单次 launch 的空 kernel 开销：Python 路径 8.5 µs，同一批 kernel 用 CUDA Graph 后摊到 0.85 µs/个，固定重放开销约 3.6 µs。还验证了 4 个 stream 并发能把 4 个串行 kernel 从 4.31 ms 压到 1.14 ms（3.79×，理论 4× 的 95%）。结论：**单 kernel 已经到墙，剩下的搜索空间在调度层**——但按 Amdahl，如果 kernel 本身只占 65%，调度优化最多再拿 25%，所以我判断投入产出比不高，没有继续。

**追问预警**：为什么不用 Graph 上生产？→ Graph 要求形状固定、不能有动态分支/host 回读；decode 阶段 batch 会变，所以 vLLM 只在特定场景用。

### C1. 你的项目有什么局限

> 三个：① 所有 kernel 都在 8 GB / 272 GB/s 的笔记本 GPU 上跑，结论是"在这张卡上到墙"，换 A100/H100 需要重新算 AI 和并行度；② 没有真机多卡/分布式经验，只写了概念笔记；③ PagedAttention 只覆盖 decode 单 token，没有 prefill 和 continuous batching。

### C2. 你接下来想做什么

> 想进算子/推理方向做性能工程：把"算字节账 → 判瓶颈 → 换实现"这套方法用到真实模型上，而不是教科书例子。短期想补的是 prefill/GEMM 的 Tensor Core 深水区（TMA、cp.async、swizzle），这些我在 GEMM 台阶4 只摸到门槛。
