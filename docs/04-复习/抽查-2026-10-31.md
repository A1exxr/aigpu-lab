## 一、老题（来自 w2_reduce / w2_softmax / w2_gelu）

### O1 · Reduce（`w2_reduce.cu`：0.1137 ms / 54.3% 标称；ncu `dram 87.25%` `sm 39.08%` `warps_active 94.88%` `gpu__time_duration 82.94 µs`）

**题目**
- (a) warp 内归约为什么用 `__shfl_down_sync` 而不是共享内存？省掉了什么？
- (b) DRAM 87.3% / SM 39% / warps_active 94.9% 三个数一起说明什么？还能不能优化？

**用户答案（8+4 = 12 / 33）**
- (a)「直接读别的线程的寄存器值，不通过共享内存，更快」——✅ 方向对，但漏了省掉的东西。
- (b)「DRAM 87.3% 说明带宽到顶、warps_active 94.9% 说明占用率高；SM 39% 是什么？block 不够吗？加点 block？」——❌ 前半对，后半错。

**标准答案**

(a) shuffle 在**寄存器之间直传**，省掉三样：
1. 写共享内存（store）；
2. 读共享内存（load）；
3. 这两步之间那道 `__syncthreads()`。

外加省容量（`__shared__` 数组），以及省掉 smem 访问的 bank conflict 风险。warp 内 32 个 lane 由同一个 scheduler 调度、能直接对齐，`__shfl_down_sync` 一条指令就完成一次 offset 交换（16→8→4→2→1，5 轮、**零屏障**）。

(b) 三个数各管一件事，一起看才成立：

| 数 | 含义 | 本例判定 |
|---|---|---|
| `dram__throughput` 87.3% | 显存总线用了多少 | **已到墙** |
| `warps_active` 94.9% | 驻留 warp 占上限多少 | 占用率不是瓶颈 |
| `sm__throughput` 39.1% | 计算流水线忙的比例 | **低是应该的**（线程在等显存） |

签名 `DRAM 高 + warps_active 高 + SM 低` = **标准的访存受限**，不是缺陷。

如果真是「block 不够」，先掉下来的会是 `warps_active`（例如 50%），而不是 SM。

结论：`reduce` 不能再快——读 16 MiB 是问题本身要求的（每个元素都要读一次相加），**只能换问题，不能优化 kernel**。（另：bench 报 54.3% 与 ncu 报 87.3% 是两把尺子，见 `docs/02-实验/` 里「两把尺子」一节。）

### O2 · Softmax（`w2_softmax.cu`：屏障 20 → 4，0.2160 ms / 57.1%；ncu `sm 87.96%` `dram 38.20%`）

**题目**
- (a) 从 20 个屏障降到 4 个，具体去掉了哪些？
- (b) 为什么再往下减收益递减？

**用户答案（6+2 = 8 / 33）**
- (a)「归约都改成线程级归约，线程级不需要屏障，只有广播时一个屏障」——✅ 方向对，但没说出「去掉的是哪几个」。
- (b)「不知道」——❌

**标准答案**

(a) 原版每个**逐行归约**都是「两级归约」的标准写法，每次要 2 个屏障：

```
写 smem[ty][warp]  → 屏障 → 读 → 算 → 写回 smem[ty][0] → 屏障 → 广播读
                    ↑①                          ↑②
```

一行 softmax 要 3 次逐行归约（求 max、求 sum、exp 后求 sum×），外加 exp 前后的同步 → 20 个。

降到 4 的办法：**级别 1 全部换成 warp shuffle**（warp 内零屏障），只保留「跨 warp」那一段：

```
每行：warp 内 shuffle 归约（0 屏障）
      → lane 0 写 smem[ty][warp_id]
      → 屏障 ①（1 个）
      → warp 0 读 smem[ty*8..] 做第二轮 shuffle
      → lane 0 写回 smem[ty][0]
      → 屏障 ②（1 个）
      → 全 block 广播读
```

所以每行归约 2 个屏障。整条链只剩「max 行 2 个 + sum 行 2 个」= **4 个**。

(b) 看两轮实测的**屏障单价**：

| 版本 | 屏障数 | 时间 | 每减一个屏障省 |
|---|---|---|---|
| 20 屏障 | 20 | 0.2478 ms | — |
| 10 屏障 | 10 | 0.2212 ms | **2.66 µs** |
| 4 屏障 | 4 | 0.2160 ms | **0.87 µs** |

两件事：
1. 单价从 2.66 掉到 0.87 µs —— 因为后一轮减掉的是「级别 1 的屏障」，它们夹在密集计算之间，本来就能被其他 warp 掩盖；
2. 剩 4 个 × ~0.87 µs ≈ 3.5 µs，只占 216 µs 的 **1.6%**。再减最多拿 1–2%。

**Amdahl**：瓶颈已经从屏障转移了。ncu 显示 `sm 87.96%` `dram 38.20%` → 现在是 **SM 吞吐受限**（shuffle 与 exp 的指令吞吐），不是同步。

### O3 · GELU（`w2_gelu.cu`：朴素 0.1956 ms / 63.1%；`float4` 坏版 **0.6390 ms / 19.3%**；`__half2` 好版 **0.1516 ms / 81.4%**）

**题目**
- (a) `float4 box; reinterpret_cast<half*>(&box)` 为什么慢 3 倍？
- (b) 怎么用 ncu 区分「取地址导致物化」和「寄存器真溢出」？
- (c) 为什么 `__half2` 版没这问题？

**用户答案（8+2+0 = 10 / 34）**
- (a)「寄存器里没有 box 的地址，要取地址就得通过 L1/L2 到显存去取地址」——🟡 方向对，机制说反了。
- (b)「看 per-thread-register 类似的参数，看寄存器用了多少个」——🟡 指标名对，方向没说。
- (c) 未答——❌

**标准答案**

(a) **不是「去显存取地址」，而是「数据被搬进了 local memory」。**

- 寄存器**没有地址**。一旦写 `&box`，编译器就无法把 `box` 放在寄存器里；
- 它必须把这块变量**物化**到 local memory（物理位置在显存，访问经 L1/L2 缓存）；
- 之后每次 `reinterpret_cast<half*>(&box)[k]` 都是一次真实的 local memory 访存。

结果：每线程 18 次碎片访存（4 次装 + 14 次取用），实测比朴素版慢 **3.3 倍**（0.6390 vs 0.1956 ms），带宽 19.3%。

(b) **看 `launch__registers_per_thread`，两个方向相反：**

| 现象 | `registers_per_thread` | 其他信号 |
|---|---|---|
| 取地址 → 物化到 local memory | **偏低**（数据不在寄存器里了） | `local_op_ld/st` 非 0 |
| 寄存器不够 → 溢出（spill） | **很高**（编译器硬塞很多） | `local_op_ld/st` 也非 0，但 `registers` 顶到 255 或远超预期 |

区分点就是**寄存器数的方向**，不是「有没有 local 访存」（两者都有）。

(c) `__half2` 版**全程零 `&`**：

```cpp
const __half2* x2 = reinterpret_cast<const __half2*>(x) + (size_t)i * 4;   // 指针本身，不是取局部变量地址
for (int k = 0; k < 4; ++k) {
    float2 f = __half22float2(x2[k]);        // 值 → 值（convert）
    __half2 g = __float22half2_rn({...});    // 值 → 值
    o2[k] = g;
}
```

- `x2[k]` 是**指针间接寻址**（正常全局访存），不是「取局部变量地址」；
- `__half22float2` / `__float22half2_rn` 是 **convert（值→值）**，与 `reinterpret_cast`（内存→内存）本质不同；
- 每线程 4 个 `__half2` = 8 个 half，全在寄存器；且每指令 4 B（=2 个 half），比 `half` 版少一半指令 → 81.4%，追平 PyTorch。

## 二、新题（来自 w10 LayerNorm 反向 / w8 INT8 / w6 GEMM）

### N1 · LayerNorm 反向（`w10_layernorm_backward.cu`：0.2980 ms / 81.8% 实测；ncu 277.9 µs、`registers 48`、占用率 81.2%、`dram 80.6%`）

**题目**
- (a) 流量为什么是 **6N** 而不是 7N？少读的那 1 份是什么、为什么可以不读？
- (b) 为什么必须同时留住 `x`、`x̂`、`dy` 三份数据？
- (c) 4 次归约（mean、var、dot、sum）为什么不能合并成 1 次？

**标准答案**

(a) 6N = 读 `x`（2N）+ 读 `dy`（2N）+ 写 `dx`（2N）。（N = 元素个数 × 2 B；`2048×4096` fp16 时 6N = 48 MiB。）

**少读的那 1 份是 `x̂`**。因为 `x̂ = (x − mean)·rstd`，mean 和 rstd 算完就在寄存器里，可以**现场重建** x̂，不必再把 normalize 的结果写出去、再读回来。

对比：如果拆成两个 kernel（`normalize` 一趟 + `backward` 一趟），就要多写一次 + 多读一次 x̂ → 7N 甚至 8N。

(b) 因为 `dx` 的公式里三份数据都在**同一行内被复用两次以上**：

```
dx_i = rstd · ( dy_i − mean(dy) − x̂_i · mean(dy·x̂) )
                    ↑ 用 dy         ↑ 用 x̂
       ↑ 还要 x（重建 x̂ 用）
```

- `dy_i` 用在三处：`mean(dy)`、`mean(dy·x̂)`、最后的 `dy_i − ...`；
- `x̂_i` 用在两处：`mean(dy·x̂)` 与最终乘法；
- `x_i` 用来重建 `x̂_i`（也可直接存 x̂）。

任一份不留，就得回头看显存 → 多 2N 流量。全部留在寄存器里，是靠「每线程 16 个元素 + 宏展开 + 常量下标」实现的（数组下标必须是编译期常量，否则会退到 local memory）。

> 注：这版是**寄存器驻留**，不是共享内存驻留。若真放共享内存，三份各 `256×16×2 B = 8 KB`，合计 24 KB。

(c) 最少是 **2 趟**，不是 1 趟：

- 第 1 趟求 `sum(x)`、`sum(x²)` → 才能得 mean、rstd（**数据依赖**）；
- 第 2 趟才能算 `x̂`，才有 `sum(dy)`、`sum(dy·x̂)`。

所以理论上界是 2 趟（把 mean/var 合并、把 dy 的两个和合并）。现在写成 4 次，是因为**4 次都单独调用了 `block_reduce`**——每次自带 3 个屏障。用 K-07 那招（`float2` 一趟带回两个值）可以把 4 次降到 2 次，省的是**屏障**（12 → 6），不省字节，也不省 shuffle 总数（32 次不变）。

### N2 · INT8 PagedAttention（w8 实证：①fp16 split-L 1.2483 ms / 215.1 GB/s；②只量化 K 1.0419 ms / 194.4 GB/s / **87.8%**；③K+V 都量化 1.2032 ms / 113.4 GB/s / **51.2%**；④K+V+`int8×4` 1.5503 ms；⑤K+V+split-L 1.1223 ms）

**题目**
- (a) 流量 193 → 130 MiB（−33%），时间却从 1.0419 涨到 1.2032 ms。用「在飞字节」定量解释。
- (b) 这说明「省字节」和「保每指令字节」哪个优先？
- (c) `int8×4` 用一条 `int` 加载 4 个字节，救的是哪个数？

**标准答案**

(a) **Little's Law**：稳定状态下

```
带宽 ≈ 同时在飞的字节数 / 访存延迟
在飞字节 ≈ SM 数 × 每 SM warp 数 × 每 warp 每指令字节 × 同时未完成的指令数
```

对 fp16 的 K/V 读取，warp 内 32 个 lane 各自读 2 B（或 `__half2` 读 4 B）→ **每 warp 每条指令 64 B（或 128 B）**。
对 int8，每 lane 读 1 B → **每 warp 每条指令只有 32 B**。

虽然总字节少了 33%，但**同样是「每 lane 一条指令」的循环次数没变**，每指令搬的字节少了 2–4 倍 → 在飞字节反而少了 → 带宽利用率从 87.8% 掉到 51.2%，净变慢 **15.5%**（1.0419 → 1.2032 ms）。

(b) **先保「每指令字节」，再谈省字节。** 或者说：省字节只有在你**同时把每指令字节数提上去**（或请求数能补上）时才兑现成时间。

一句话：**量化省的是带宽需求，向量化保的是发射能力；缺了后者，前者白省。**

(c) `int8×4` 救的是**每指令字节数**：32 B/warp → 128 B/warp（和 `__half2` 打平），指令数降回原水平。它**不改变** 130 MiB 这个总量。

代价是拆字节（符号扩展 `(int8_t)(k4 >> 8)`）与 q 侧 `__half2` 对齐，以及 acc 的 lane 映射要从 `lane + 32k` 改成 `4*lane + k`——归约和写回都要跟着改。

### N3 · GEMM 台阶3（`w6_gemm.cu`：naive 2.4207 ms → tiled 1.7838 ms → 寄存器分块 0.6574 ms → `wmma` 0.2836 ms / 1.13× vs PyTorch fp32）

**题目**
- (a) 为什么共享内存读取次数是 **4 倍**（不是 tiled 的 1 倍、也不是 16 倍）？用「一次读服务几次 FMA」推。
- (b) `[32][33]` 那个 padding 为什么在这个 kernel 里没用？
- (c) 台阶4 的 `wmma` 为什么彻底绕开了 bank conflict？

**标准答案**

(a) 用「每读服务几次 FMA」推：

| 版本 | 每个 `kk` 迭代 | 读 smem | FMA | 每次读服务的 FMA |
|---|---|---|---|---|
| tiled（每线程 1 个 C） | `As[ty][kk]`、`Bs[kk][tx]` | 2 | 1 | **0.5** |
| 寄存器分块 4×4 | 4 个 A + 4 个 B | 8 | 16 | **2** |

每次读服务的 FMA 提高了 **4 倍**（0.5 → 2），等价地：摊到每个 C 元素上的 smem 读次数是 tiled 的 **1/4**。

（另一条算法也对：tiled 每个 C 元素要 2K 次 smem 读 = 2048 次；寄存器分块 8×(K/1)=8192 次分给 16 个 C 元素 = 512 次/元素 → 2048/512 = **4×**。）

(b) padding 的规则是「让同一列的元素跨行时错开 **整数个 bank（4 B）**」。[32][33] 是为 **4 B 元素**（float）设计的：行跨度 33×4 = 132 B = 33 bank，正好错开 1 个。

这里的元素是 **2 B 的 half**：行跨度 33×2 = **66 B = 16.5 bank** —— 半个 bank。同一列相邻行落在同一个 4 B word 的**两个半区**上，地址不是 4 B 对齐 → 访问会跨 bank 边界，冲突反而增加。实测 [32][33] 是 **2.5160 ms**，比不 padding 的 1.7838 ms **慢 41%**。

（half 要想 padding，应该用 `[32][32 + 2]` 这种「66×2 = 132 B」的跨度，即加 2 个元素，而不是加 1 个。）

(c) `wmma` 的 `fragment` **本身就存在寄存器里**，`mma.sync` 直接吃寄存器，不再有「手写 smem 读取模式」：

```cpp
load_matrix_sync(a_frag, As + ..., ldm);   // 一次性搬进 fragment（编译器生成最优序，含 swizzle）
mma_sync(c_frag, a_frag, b_frag, c_frag);  // 纯寄存器运算
```

bank conflict 是「手写 load 的地址模式」带来的问题；数据一旦由 `load_matrix_sync` 成块搬进寄存器，这个层面就消失了。

代价：必须按 16×16×16 的粒度、满足 `ldm` 与对齐要求、且 accumulator 用 fp32 后再转 fp16 写回。

## 三、这一轮要记住的三句

1. **三个百分比各管一件事**：DRAM 看带宽、warps_active 看并行度、SM 看计算流水线。`DRAM 高 + warp 高 + SM 低` = 访存受限，是正常签名，别再调。
2. **「取地址」不是「去取地址」，是「数据被赶进 local memory」**。区分它和溢出，看 `registers_per_thread` 的方向（物化偏低、溢出很高）。
3. **省字节 ≠ 变快**。INT8 那 33% 的字节被「每指令字节掉 2–4 倍」吃掉了，还倒亏 15%；必须 `int8×4` 配套才兑现。

## 四、附：我在这一轮里纠正的两处自己的错

1. **「结尾补一道屏障 → 13 个」是错的。** 正确：两种排法成本相同——开头屏障版 4 次调用 12 个（首个浪费 → 有用 11），结尾屏障版 12 个（末次浪费 → 有用 11）。差别只在代码整洁度，不在屏障数。
2. **问代码细节却不给代码**（Q2(b)(c) 那次）。以后凡涉及 `16` / `256` 这类硬编码，题目里必须附上那段代码。
