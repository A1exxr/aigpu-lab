## 二、逐项要点（只记"为什么"，不记代码）

### 1. Reduce —— 两级归约
- 级别 1：寄存器累加 + warp shuffle（`__shfl_down_sync`，offset 16→1，零屏障）
- 级别 2：每 warp 一个值 → 共享内存 → 1 次屏障 → warp 0 再 shuffle
- **结论：DRAM-bound，87.3% 已贴墙，不能再优化。**
- 追问：为什么 shuffle 比共享内存快？（无屏障、无 banks 冲突、走寄存器）

### 2. Softmax —— 屏障成本
- 20 屏障 0.2478 → 10 屏障 0.2212 → 4 屏障 0.2160
- 级别 1 屏障成本 2.66 µs/次，级别 2 只有 0.87 µs/次 → **收益递减**
- ncu：SM 87.96% / DRAM 38.20% → **SM-bound 不是带宽-bound**
- 追问：还能再减少屏障吗？（warp 内合并 + 每 warp 独立处理一行）

### 3. GELU —— 向量化与 local memory
- 三版：朴素 0.1956（63.1%）→ `float4`+`&box` **0.6390（19.3%，慢 3.3 倍）** → `__half2` 0.1516（81.4%）
- **`&box` 取地址 ⇒ 变量被迫物化到 local memory（物理在 DRAM），18 次碎片访存**
- 判据：`launch__registers_per_thread` —— 溢出=很高，取地址=很低
- 追问：`__half2` 省的是什么？（指令条数，不是字节数）

### 4. Fused RMSNorm —— 融合的极限
- 两步版：add(76.2%) + rmsnorm(83.8%)，合计 390 µs，5 流 80 MB
- 融合版：3 流 48 MB，199.9 µs，92.8%
- **理论天花板 1.25×，实测 1.95×**（因为两步版各自也没到墙）
- 追问：还能融合什么？（attention 的 QK+softmax+PV 已是 w5 做的事）

### 5. Attention naive —— 扇区利用率
- 起点 46.9 ms（0.09× 基线）→ 1 个改动（warp-per-j）→ 24.91 ms
- 关键数：跨行读 K 时 warp 内 32 个地址间隔 128 B ⇒ 每个 32 B sector 只用 2 B ⇒ **6.25%**
- 后续：PV 四路拆分 18.83 → ILP-4 展开 **15.5 ms**
- 追问：为什么 warp-per-j 就对了？（同一 j 的 d 连续，32 lane 拼成 64 B = 2 sector 满载）

### 6. FlashAttention（Triton）—— 算法层
- 0.474 ms / 18.1 TFLOPS（27.8% 峰值）/ SDPA 的 91%
- 关键：不写 S² 中间矩阵，块内 online softmax（running max + rescale）
- 追问：flash 的代价是什么？（重复读 K/V：每行读 L/B_n 次，靠 L2 扛）

### 7. GEMM 四台阶 —— 逐级榨干
| 台阶 | 做法 | 时间 | 相对 |
|---|---|---|---|
| 1 naive | 每线程 1 元素，直读全局 | 2.42 ms | 1× |
| 2 tiling | 32×32 共享内存块 | 1.784 ms | 1.36× |
| 3 寄存器分块 | 每线程 4×4，block 8×8 | **0.6574 ms** | 3.7× |
| 4 Tensor Core | wmma 16×16×16 | **0.284 ms** | 8.5×，超 torch fp32 1.13× |
| 4b 反例 | 64×64 tile | 0.3758 ms | 更慢：24 KB smem ⇒ 占用率掉 |
- **共享内存读取摊薄 4 倍**（每读服务 4 次 FMA）
- 追问：为什么只到 1.13×？（缺 warp 级 mma、缺双缓冲 pipeline、缺 swizzle）

### 8. PagedAttention —— 4 个台阶
| 版本 | 时间 | 带宽 | 说明 |
|---|---|---|---|
| 两遍（先 softmax 再 PV） | 2.3644 ms | 170.3 GB/s | 中间写回 S 向量，384 MiB |
| 单遍 online | 1.8897 ms | 142.1 GB/s | 256 MiB，省 33% |
| +2 路展开 | 1.5084 ms | 178.1 GB/s | ILP |
| **split-L** | **1.2483 ms** | **216.0 GB/s / 97.6% 实测** | 拆 L 补并行度 |
- 追问：为什么联不上"块映射"？（块映射改的是访存地址，不减少字节；split-L 才补并行度）

### 9. INT8 —— 一个正例三个反例（最有价值的一节）
| 版本 | 时间 | 带宽(实测%) | 结论 |
|---|---|---|---|
| 只量化 K（per-token scale） | **1.0419 ms** | **87.8%** | 正例：字节 193→163 MiB，真赚 |
| KV 全量化 | 1.2032 ms | 51.2% | 反例：两条流都变窄，warp 每指令只 32 B |
| + vec4 打包 | 1.5503 ms | 40% | 反例：寄存器压力和拆分开销吃掉收益 |
| + split-L 搬回并行度 | 1.1223 ms | 55% | 反例：仍不如 ⑤ |
- **一句话结论：量化省字节，向量化保"每指令字节数"，两者必须配套。**
- 追问：scale 为什么是 fp16 不是 fp32？（数值上够用，且跟着 K/V 一起搬，不增加一条流）

### 10. 调度层 —— 到墙之后
- 空 kernel launch 开销 **8.52 µs**（C++ 版，Python 版测出 13.6）
- graph：`t = 3.6 + 0.88N` µs；N=64 时 **61.4 → 8.52 µs**
- 多流：4 个独立的串行 5618 µs → 并发 1516 µs（**3.79×**）
- **结论：单 kernel 优化到 90%+ 之后，收益来自"少启动、少等待"，不是"少搬字节"。**
- 追问：graph 为什么不能全用？（有捕获一次性成本、显存地址固定、动态形状不友好）
