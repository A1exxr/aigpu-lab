# 概念：GPU 上的"并行"不止 kernel 内部——stream / event / CUDA Graph

> 为什么现在学这个：你的 decode kernel 已经做到 1.04 ms ≈ 87.8% 带宽，**单 kernel 到墙了**。
> 剩下能压的只有 kernel **外面**的东西：排队、启动、多个 kernel 之间能不能重叠。
> 这也是推理引擎（vLLM / TensorRT-LLM）真正在做的第二层优化。
>
> 读法：先看 §1 的图，再看 §2 的四个 API，§3 是本机实测的坑（你已经踩过一个），§4 是三个实验。

---

## 1. 一次 kernel 启动，到底发生了什么

```
CPU:  写参数 → 调用 kernel<<<grid, block>>>  →  [ 入队 ]  →  继续跑下一行 C++（异步！）
                                              ↓
GPU:                                     命令队列（硬件 queue）
                                              ↓
                                    调度器挑一个 SM 分配 block
                                              ↓
                                        kernel 执行完
                                              ↓
                        （如果 CPU 调了 cudaDeviceSynchronize / .cpu() / event 同步）才能看到结果
```

关键事实：**kernel 启动是异步的**。CPU 把命令塞进队列就返回，一个 kernel 的"提交"只要 **2–10 µs**（本机实测，见 §3），但 GPU 执行可能要 1 ms。

- kernel 执行时间 ≫ 提交开销 → 你是 **compute/bandwidth-bound**，优化 kernel 内部（你已经做完）
- kernel 执行时间 ≈ 提交开销 → 你是 **launch-bound**，优化"少启动、重叠启动"

decode 恰好落在后者的边缘：1.04 ms 不算小，但真实推理里 `decode` 每生成 1 个 token 就要启动一次，**每 token 一次启动 × 32 层 × 每层 3–4 个 kernel = 每 token 上百次启动**。这时候 5 µs 的启动开销叠起来就是 0.5 ms/token——比 kernel 本身还大。

## 2. 四个东西，一次说清

### 2.1 stream（流）
一条 stream 就是一个**命令队列**。同一个 stream 里的操作**严格按顺序执行**；不同 stream 之间**可以并发**（硬件允许时）。

```cpp
cudaStream_t s1, s2;
cudaStreamCreate(&s1);
cudaStreamCreate(&s2);
kernel_a<<<g, b, 0, s1>>>(...);   // 第 4 个参数是 stream，默认 0 = 默认流
kernel_b<<<g, b, 0, s2>>>(...);   // 和 a 可能重叠
```

**"可能"重叠**的前提（三条都要满足）：
1. GPU 还有空余 SM / 空余 warp 槽位（你的 decode 只用了 32 个 block，24 个 SM 上还空着）；
2. 两个 kernel 没有数据依赖（不读写同一块显存）；
3. 硬件支持并发（compute capability ≥ 2.0 都支持，但**分时切片**，不是真同时）。

> 反直觉点：kernel 并发**不是免费的并行**。两个各占 50% SM 的 kernel 并发，总时间可能和串行一样——只是把空闲的 SM 填上了。对 decode 这种"每 SM 只有 1.33 个 block"的负载，并发才有意义。

### 2.2 event（事件）
给 stream 打时间戳/同步点，用来**测时间**或**跨流同步**。

```cpp
cudaEvent_t e0, e1;
cudaEventCreate(&e0); cudaEventCreate(&e1);
cudaEventRecord(e0, s1);          // 在 s1 当前位置插一个标记
kernel<<<..., s1>>>(...);
cudaEventRecord(e1, s1);
cudaEventSynchronize(e1);         // 等 e1（只等这一条流）
cudaEventElapsedTime(&ms, e0, e1);// 得到 GPU 上的真实耗时
```

为什么不用 `std::chrono`：CPU 时钟测的是"提交耗时"，不是"GPU 执行耗时"。你的 bench 用的就是 event 计时。

### 2.3 CUDA Graph（图）
把一串固定的 kernel 启动 + 内存拷贝**录下来**，之后一次性提交整张图。

```cpp
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
  for (int i = 0; i < 32; ++i) kernel<<<g, b, 0, s>>>(...);   // 只录，不执行
cudaStreamEndCapture(s, &graph);
cudaGraphInstantiate(&exec, graph, 0);
cudaGraphLaunch(exec, s);        // 一次调用 = 提交 32 个 kernel
```

收益：把 N 次 ~5 µs 的提交压成 1 次。本机若 32 个 kernel，理论上省 ~150 µs。
代价：参数被**录死在图里**（指针、dim3 都是快照），输入地址变了要重建图或改节点参数；动态控制流不支持。

### 2.4 三者的关系一句话
> stream 管**顺序与重叠**，event 管**计时与跨流依赖**，graph 管**减少提交次数**。

## 3. 本机（RTX 4060 Laptop + WSL2）已经踩过的坑

| 坑 | 现象 | 原因 | 处理 |
|---|---|---|---|
| **CUDA Graph 捕获为空** | `cudaStreamEndCapture` 返回 success 但图里 0 个节点，或报 "operation not permitted when stream is capturing" | 用了**默认流**（legacy default stream）。默认流是"隐式同步流"，捕获时禁止隐式同步 | 捕获必须用**非默认流**（`cudaStreamCreate`），或编译时开 `--default-stream per-thread` |
| PyTorch 里同理 | `torch.cuda.graph(g)` 报错 | PyTorch 默认用 legacy default stream | 用 `torch.cuda.graph(g)` 的上下文（它内部会切到 side stream）+ 先 `torch.cuda.synchronize()` |
| **ncu 和 torch.profiler 打架** | ncu 一跑就卡死/无输出 | 两者都用 CUPTI，不能同时挂 | 用 ncu 时先 `import os; os.environ["CUDA_INJECTION64_PATH"]=""`？不，正确做法是**不要在 ncu 下跑 profiler**，或改用独立脚本 |
| WSL2 时钟 | `nvidia-smi -lgc` 不支持 | WSL 不透传锁频 | 只能靠多跑几次取中位数 |

## 4. 三个实验（每个 20–30 分钟，按顺序做）

> 目标不是"学会 API"，是拿到**三个数字**，能回答面试里那句"你怎么知道瓶颈不在 kernel 里"。

### 实验 A：测 launch overhead（这是前提）
写 3 个 kernel：空 kernel、只写 1 个元素的 kernel、真正的 decode。
各启动 1000 次，测总时间 / 1000。

**判据**：
- 空 kernel ≈ 2–10 µs/次 → 这就是你的 launch 成本
- 如果 decode 的 1.04 ms 里，这个数字占比 < 1% → **不是 launch-bound，实验 B/C 收益有限**

### 实验 B：多 stream 并发跑 decode
把 `B=8` 个请求拆成 4 组，跑在 4 条 stream 上；对比单 stream 串行跑 4 次。

**判据**：
- 总时间下降 > 15% → decode 的 block 数（32）确实喂不饱 24 SM，并发有收益
- 没变化 → SM 已经被占满，或者 DRAM 带宽已打满（你 87.8%，接近）

### 实验 C：CUDA Graph 捕获同一组 kernel
把"4 组 decode"用 graph 录下来，对比不录的版本。

**判据**：
- 省下的时间 ≈ 4 × launch 成本 → graph 生效
- 报 `operation not permitted` → 你踩了默认流的坑，改用非默认流重试

### 实测结果（2026-10-27，RTX 4060 Laptop + WSL2）

**A：launch 开销**

- 空 kernel 连发：**8.2–11.2 µs/次**（这是"从 Python 提交一次"的完整成本，不是 CUDA 原生 launch）
- 对照：PagedAttention decode 1040 µs → launch 占比 **0.8%** ⇒ 单 kernel **不是 launch-bound**

**B：多 stream**

- 空 kernel：单流 10.58 µs/次 → 4 流 **8.35 µs/次**（快 21%）
  - 这 21% 来自 **CPU 提交流水线**（GPU 执行 A 的同时接收 B 的提交），**不是 GPU 并行**——空 kernel 没有计算可并行
- 4 个 spin kernel（每个 5618 µs）：串行 4×5618 → 4 流并发 **1516 µs**，**3.71×**（理想 4×，效率 93%）
  - 原因：每块只 1 个 block 的 kernel 只占 1 个 SM，24 SM 用了 1 个 → 并发才有空间

**D：graph 收益是否随 N 线性**

| N | 整批 µs | 每节点 µs | 比单发省 µs |
|---|---|---|---|
| 1 | 8.2 | 8.19 | 0.33 |
| 8 | 10.0 | 1.24 | 7.27 |
| 32 | 29.7 | 0.93 | 7.59 |
| 64 | 61.4 | 0.96 | 7.56 |

最小二乘：`graph 整批 ≈ 3.6 µs（固定）+ 0.88 µs × N`
⇒ 重放一张图固定 3.6 µs（就是一次提交的价格），图内**每节点 0.88 µs**，每层省 7.6 µs 恒定 → **线性**。

**D：真并发**（`exp_sched.cu`，4 个 spin kernel 各占 1 个 SM）

- 单个 spin kernel 1549.3 µs（2,835,000 cycles → 反推 SM 实际频率 **1.83 GHz**，标称是 2.65 GHz）
- 串行 4 次 4309.0 µs → 4 流并发 **1135.6 µs**，**3.79×**，效率 **95%**
- 这才是 GPU 真并行：24 个 SM 只用了 1 个，并发把它们用满

### 4.5 一个必须说清的口径：这 8.5 µs 是谁的钱（**已用 C++ 实测推翻初版结论**）

初版我猜"8.2 µs 里约 6 µs 是 Python 绑定开销"。**实测证伪**：用纯 C++（`kernels/exp_sched.cu`，一次 pybind 都不经过）测同样 1000 次连发：

| 提交方式 | 每次成本 |
|---|---|
| Python 循环 `mod.empty_launch()` | 8.2 µs |
| **纯 C++ 循环 `empty_kernel<<<1,32>>>()`** | **8.52 µs** |
| graph 重放（图内每节点） | 0.88 µs |

两者几乎相同 ⇒ **pybind 不是瓶颈**。8.5 µs 是**这条提交路径本身的成本**——WSL2 上每次 CUDA 调用要走虚拟化层，原生 Linux 通常只要 1–2 µs。所以正确说法是：

> "在 WSL2 上每次 kernel 提交约 8.5 µs，切换语言不变（Python 8.2 / C++ 8.5），说明贵的是 GPU 调用路径而不是语言绑定。"

`g.replay()` 之所以便宜，是因为**一次提交带 N 个节点**——它省的不是"Python 税"，是 **N−1 次提交**。

### 4.6 顺带被证伪的第二个假设：多流能"流水线化提交"

| 口径 | 单流 | 4 流 |
|---|---|---|
| C++（`exp_sched.cu`，取最小 9 轮） | 8.52 µs | **9.08 µs（更慢 6.7%）** |
| Python（v2 脚本） | 10.58 µs | 8.35 µs（快 21%） |

C++ 里多流**没有收益**，还因为多了 4 次 `cudaStreamSynchronize` 而略慢。Python 那次 21% 不可复现 → 判定为噪声，**"提交流水线能省 launch 成本"这个说法在本机不成立**。

真正验证"并发"的是下面的 D 实验（真 workload，3.79×），它靠的是空 SM，不是流水线。

## 5. 做完之后你应该能回答的问题

1. 你的 decode kernel 是 launch-bound 还是 bandwidth-bound？依据是哪个数字？
2. 多 stream 并发在什么条件下**没有**收益？（答：SM 已满 / 带宽已满 / 有数据依赖）
3. CUDA Graph 为什么不能捕获默认流？（答：默认流带隐式同步语义，捕获时无法保证图是纯静态的）
4. 真实推理引擎为什么每层都要 graph 或 fusion？（答：每 token 上百次启动，提交开销累积）

## 6. 和你的项目怎么接上

做完这三个实验，你的 PagedAttention 故事会多一层：

> "单 kernel 到 87.8% 带宽之后我测了 launch 开销：**8.5 µs/次，占 decode 的 0.8%**，所以单 kernel 不是 launch-bound。为了排除语言干扰，我又用纯 C++ 重测了一遍——**8.52 µs，和 Python 的 8.2 µs 几乎一样**，说明贵的是 WSL2 上每次 GPU 调用本身，不是 pybind。真实 decode 每 token 要启动几十到上百个 kernel，所以接着测了两层：4 stream 并发在真 workload 上 **3.79×**（空 kernel 没有收益，因为并发需要空 SM）；CUDA Graph 重放固定 **3.6 µs**、图内每节点 **0.88 µs**，每层省 7.6 µs 且严格线性，拐点在 N≈0.5。结论：**单 kernel 优化到这里为止，剩下的收益在调度层——它省的是提交次数，一次提交能带 N 个节点。**"

这句话在面试里的分量，比"我又优化了 5%"大得多——它证明你知道**优化有边界，而且知道边界在哪**。
