# 如何写你的第一个 CUDA kernel

> 这篇不讲 CUDA 语法（那些教程里有），只讲**怎么从零走到通过验收**。
> 核心方法：**把第一步缩小到不可能失败，然后一步步加。**

---

## 0. 先破除一个误解：优化空间比你想的小

看实测数据（你这张卡，`results/baseline.md`）：

| 算子 | 带宽利用率 | 性质 |
|---|---|---|
| gelu（逐元素） | **82.5%** | PyTorch 已接近实用上限 |
| layer_norm | 79.8% | 同上 |
| residual_add | 80.0% | 同上 |
| **scale（那个平凡的 memcpy 型 kernel）** | **81.4%** | 见下 |

再看 `--harness-test` 里那个**只有 8 行**的 kernel（`out[i] = in[i] * factor`）：
**221.4 GB/s，81.4% 带宽利用率，加速比 1.01x。**

**这说明两件事，都很重要：**

1. **一个平凡的逐元素 kernel 就能打满带宽。** 所以：
   > **在纯逐元素算子上，你的目标不是"打败 PyTorch"，而是"追平"（~82%）。**
   > 带宽已经饱和了，再怎么调 `block_size` 也就几个百分点。
2. **真正能打败 PyTorch 的地方在"减少访存趟数"**，也就是 **W3 的算子融合**。
   朴素 RMSNorm 跑 1.378ms、只有 9% 带宽利用率 —— 不是它写得差，
   是它**多跑了好几趟 HBM**。

**所以 W2 的验收标准（>70%）是"及格线"，不是"目标线"。真正的战场在 W3。**

## 2. 增量阶梯：每一步都很小，每一步都能验证

**不要想着"一次写出最好的 RMSNorm"。** 按下面这条阶梯走，
每一步都跑一次 `bench_kernels.py` 看结果，走完你就到 W2 验收了。

### 阶梯 0：跑通内置的 scale kernel ✅（现在就能做）

```bash
python kernels/bench_kernels.py --harness-test
```
应当看到 ~81% 带宽利用率。**这一步的意义：证明整条工具链在你这台机器上是通的。**

### 阶梯 1：创建 `kernels/w2_rmsnorm.cu`，先把 scale 抄进去改名

- 复制 `HARNESS_CUDA` 的内容到新文件
- 把函数名从 `scale` 改成 `rmsnorm`
- 参数先保持简单（`torch::Tensor x`），**先不做归约**
- 跑 `python kernels/bench_kernels.py --only rmsnorm`

**预期**：会编译失败或正确性 FAIL（因为签名和参考实现不匹配）。
**这是正常的** —— 这一步的目的只是确认"我的文件被正确加载和编译了"。

### 阶梯 2：让签名对上（不实现算法）

`bench_kernels.py` 里 `rmsnorm` 条目期望的签名是：

```cpp
torch::Tensor rmsnorm(torch::Tensor x, torch::Tensor w, double eps);
```

先让编译通过、让 `cuda_call` 能调用到你。**输出可以先不管对错。**

**预期**：编译通过 ✓，正确性 `[WRONG]`。
**这一步的意义：把"工具链问题"和"算法问题"分开。** 如果你在这里就卡住，
那说明是签名/编译问题，不是你的算法问题。

### 阶梯 3：实现最简单的版本（一个 block 处理一行）

现在才进入算法。你需要决定并**写下来**的三件事：

1. **并行映射**：谁负责哪一行？谁负责行内的哪些元素？
   - 提示：`grid.x` 对应行号是常见的起手式
2. **归约**：一行有 4096 个元素，一个 block 内怎么把它求和？
   - 这是 CUDA 最经典的练习，也是面试最爱问的
3. **两遍还是一遍**：先算平方和再算输出，还是别的顺序？

**写出最朴素的版本就行。** 不要用 warp shuffle，不要向量化 —— 那些是阶梯 5 的事。

**预期**：正确性 `[PASS]`，带宽利用率大概 30%~60%。
**这一步的意义：你有了一个能跑对的东西。从现在起所有优化都是在这上面加。**

### 阶梯 4：回答那 5 个问题

跑通之后，`kernels/README.md` 里的 5 个问题要一个个**用实测**回答：

| 问题 | 怎么测 |
|---|---|
| `block_size` 为什么是 256？ | 改成 128 / 512 / 1024，各跑一次，把带宽利用率记下来 |
| 用了什么规约策略？ | 描述你自己的实现（共享内存？树形？） |
| 共享内存用了多少字节？occupancy 多少？ | 手算 + 看 `ncu`（如果装了） |
| 有效带宽到了峰值的百分之多少？ | 看报告里的数字 |
| 有没有 bank conflict？ | 用 `ncu` 看，或改共享内存布局对比 |

**这一步才是真正的学习发生的地方。** 写出来只是第一步，能解释才叫会。

### 阶梯 5：优化到 >70%

有了阶梯 3 的基线，按这个顺序试，**每换一个就测一次**：

| 优化 | 预期收益 | 代价 |
|---|---|---|
| **`float4` 向量化访存** | 最大 | 要求元素数能被 4 整除，要处理边界 |
| **warp shuffle 规约**替代 `__syncthreads` | 中等 | 代码复杂度上升 |
| **一个 warp 处理一行** | 中等 | 行内元素数必须 ≥ 32 |
| 调整 `block_size` | 小 | 几乎为零 |
| `__restrict__` / `const` | 很小 | 零 |

**建议顺序：先向量化访存，再改规约。** 前者对带宽利用率的影响大得多。

## 3. 五个常见坑（按症状查，不按原因查）

| 症状 | 通常是什么 |
|---|---|
| 结果全是 0 或全错 | kernel 根本没被调用；或 launch 的 grid/block 覆盖不到所有元素 |
| 大部分对，边缘几个错 | **边界没处理**：`n` 不是 `block_size` 整数倍时的越界保护 |
| 结果**随机**错，重跑不一样 | 缺 `__syncthreads()`，或规约的初始值不对（用了未初始化的共享内存） |
| 结果对但很慢，带宽 < 30% | 访存没合并（步长不是 1）；或规约里 `__syncthreads` 用太多 |
| 正确性 PASS 但 `max_abs` 刚好卡线 | fp16 累加精度不够，规约应该用 fp32 累加再转回 |

> **调试技巧**：先用一个**很小**的输入（比如 2 行 × 8 个元素）跑，
> 把中间结果打印出来。大输入上的错误很难定位。

## 4. 每次改完的标准动作

```bash
# 1) 同步（如果你在 Windows 侧改了文件）
bash /mnt/e/DSH_project/aigpu-lab/sync.sh

# 2) 编译 + 验证 + 测量
python kernels/bench_kernels.py --only rmsnorm

# 3) 觉得结果可疑时，单步验证
python kernels/bench_kernels.py --only rmsnorm --iters 300    # 提高迭代数看稳定性
```

产出在 `results/kernels.md`，**它就是你简历 bullet 的数据来源**。

## 5. 什么时候算"这个 kernel 做完了"

不是"能跑"，而是这五条都能答上来：

- [ ] 正确性 PASS，且最大相对误差 < 1e-3
- [ ] 带宽利用率 > 70%
- [ ] 能说出 `block_size` 选这个值的理由，且**有对照实验数据**
- [ ] 能说出共享内存用了多少、occupancy 大概多少
- [ ] 能说出下一步还能怎么优化（哪怕还没做）

**第 5 条尤其重要** —— 面试官问"你觉得还能怎么优化"，
你要能答出具体的、有依据的方向，而不是"再调调参数"。
